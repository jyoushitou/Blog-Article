## 总体判断

这是仓库里**结构最完整**的一篇：关键字 → 类型 → 作用 → 用法 → 三语言示例 → 最佳实践，737 行一条线走到底，没跑题。但它更像一份**自己编的参考手册**，而不是一份**学习记录**——整篇几乎没有"我卡在哪"，全是"这东西是什么"。

## 写对了的地方

1. **先把最容易含糊的东西钉死了。** 语法关键字、标量类型、内置 option、editions 特性分四组，还专门标了"已废弃勿用"（`weak`、`group`、`java_generic_services`）。这种表以后每次写 `.proto` 都会回来查一次，是真正的资产。
2. **editions（2023+）单列了一节。** 大部分教程还停在 proto2 / proto3 二分法，你把 `features.field_presence`、`enum_type`、`repeated_field_encoding` 摘了出来，还给了 `edition = "2023"` 的写法——这是超前半步的。
3. **proto2 / proto3 差异表只写了五行，但抓的都是会真出事的点**：`required` 被移除、枚举首值必须为 0、默认值不可自定义。

## 一个方法上的建议

同一周你写 `using` 那篇，是有观点的——「降级是接口设计意图的表达，不是安全边界」，这句不是抄的，是想明白了才写得出来的。而 10-21 的 proto 通篇是陈述句，几乎找不到一句"我认为 / 我踩过 / 这里最容易错"。

同样七百多行，前者是笔记，后者是资料。差别不在字数，在**每节末尾那半句判断**。以后每节加一行"我的判断"，这篇就会从"能查"变成"能想"。

还有个内部不一致：`FullService` 里声明了客户端流、服务端流、双向流四个 rpc，可三语言示例全是一元调用——连 `UserService` 里那个 server streaming 的 `ListUsers`，客户端示例都没演示。声明了却没跑，说明这一段是照着文档抄的，不是自己验过的。

## 如果回到那天，我会让你只做一件事

把 `packed` 这一条讲透：一个 `repeated int32 = [1,2,3]`，用 packed 和不用 packed 各编码出多少字节、为什么。二十行代码加一张字节图，就能把"protobuf 比 JSON 小"从口号变成你亲手算过的东西。
