# C++ 语言点

# `enable_shared_from_this` 与 `bad_weak_ptr`

- `MySQLPool` 继承了 `std::enable_shared_from_this<MySQLPool>`，构造 `Guard` 时要用 `shared_from_this()` 把池留住。但单例原来是这么写的：

```cpp
MySQLPool* MySQLPool::GetConnectionPool()
{
    static MySQLPool pool;   // 函数内静态对象，裸指针
    return &pool;
}
```

- 调用 `shared_from_this()` 直接抛 `bad_weak_ptr`。

- **原因**：`enable_shared_from_this` 内部的 `weak_this` **只有在对象被 `shared_ptr` 接管时才会赋值**。静态对象从头到尾没人用 `shared_ptr` 指向它，`weak_this` 永远是空的。

- **改法**：让工厂返回 `shared_ptr`：

```cpp
std::shared_ptr<MySQLPool> MySQLPool::GetConnectionPool()
{
    // 用 new 而不是 make_shared：构造函数私有，make_shared 在类外访问不到
    static std::shared_ptr<MySQLPool> pool(new MySQLPool());
    return pool;
}
```

# 析构函数私有 + `shared_ptr` 不兼容

- 构造函数私有没事（`new` 写在成员函数里，有访问权），但**析构函数私有会让 `shared_ptr` 编译不过**：

```
error C2248: "MySQLPool::~MySQLPool": 无法访问 private 成员
```

- 因为删除器里那句 `delete p` 是在**标准库模板内部**展开的，那里没有本类的访问权限。构造函数是在你的成员函数上下文里展开的，所以能访问。

- 结论：这类单例的标准写法是 **构造私有 + 析构公开**。

- 也考虑过自定义删除器绕过去：

```cpp
std::shared_ptr<MySQLPool> pool(new MySQLPool(), [](MySQLPool* p) { delete p; });
```

- 能编过，但类型变成 `shared_ptr<MySQLPool, Lambda>`，**和 `shared_ptr<MySQLPool>` 是两个类型**，不能互转，所有签名都得跟着改，不划算。

# `inline` 变量不等于 `inline` 函数

- 想加一个全局日志开关，先在头文件写了：

```cpp
inline bool verboseLog = false;
```

- 结果链接报 `LNK2001: 无法解析的外部符号 "bool verboseLog"`。

- **原因**：`inline` 变量只有**在本翻译单元里被用到**才保证生成实体。`Worker.cpp` 里没人用它，MSVC 就不发射了；而 `MySQL_Pool.obj`、`MySQL_Connection.obj` 通过 `extern` 声明引用它，链接时找不到定义。

- 这是 `inline` 变量和 `inline` 函数的关键差别：**函数没被调用可以不生成，变量被别处引用就必须有实体**。

- **正解**：一处定义 + 其余声明。

```cpp
// Worker.cpp：唯一定义
bool verboseLog = false;

// 头文件：只声明
extern bool verboseLog;
```

# RAII 句柄：禁止拷贝、允许移动

- `Guard` 析构时归还连接：

```cpp
Guard::~Guard()
{
    if (conn != nullptr) { pool->ReConnection(conn); }
}
```

- 但它原来是**隐式可拷贝**的：

```cpp
auto g1 = pool->GetConnection();
auto g2 = g1;                 // 编译通过，两个 Guard 都持有同一个 conn
// 作用域结束 → ReConnection 被调用两次 → 同一条连接进队列两次
// → 两个线程可能拿到同一个 MYSQL* → 帧错乱、随机崩溃
```

- 改法：

```cpp
Guard(const Guard&) = delete;
Guard& operator=(const Guard&) = delete;

Guard(Guard&& other) noexcept : conn(other.conn), pool(std::move(other.pool))
{
    other.conn = nullptr;   // 必须置空，否则原对象析构时再归还一次
}
```

- 顺带一个知识点：**C++17 的保证拷贝消除**。函数返回 `Guard` 时是 prvalue，即使删掉拷贝构造也能编译：

```cpp
Guard MySQLPool::GetConnection() { return makeReturnConn(conn); }
Sql::Guard g = sqlpool->GetConnection();      // 全程零拷贝
```

# `enum class` 代替 `bool` 参数

- 提交和回滚两个 handler 逐行相同，只有最后一句不同，抽成一个函数：

```cpp
enum class TxFinish { Commit, Rollback };

RpcStatus finishTx(const std::string& txId, std::int32_t serviceId, TxFinish mode);
```

- 如果参数写成 `bool commit`，调用点就是 `finishTx(id, sid, true)`——读代码的人得回头看签名才知道 `true` 是提交还是回滚。枚举让调用点自带语义：

```cpp
finishTx(in.tx_id(), serviceId, TxFinish::Commit);
```

# `unordered_map` 的三种查法

```cpp
auto it = txTable.find(id);
if (it == txTable.end()) { return nullptr; }   // 没找到就是 end()
return it->second;
```

| 写法                      | key 不存在时      | 会不会插入 |
| ------------------------- | ----------------- | ---------- |
| `m[id]`                   | 返回默认构造值    | **会** ❌  |
| `m.at(id)`                | 抛 `out_of_range` | 不会       |
| `m.find(id)`              | 返回 `end()`      | 不会 ✅    |
| `m.contains(id)`（C++20） | 返回 `false`      | 不会       |

- 事务表绝对不能用 `operator[]`：一个不存在的 `tx_id` 会被悄悄插进去，清理线程还得收拾。

# 并发与锁

## 把 I/O 挪到锁外

`ReConnection` 归还时的销毁重建原来在锁外做：

```cpp
if (!conn->Ping())
{
    delete conn;                        // mysql_close → SSL_free
    conn = CreateConnection(TempConnect); // mysql_real_connect
}
```

- 200 个线程同时归还时，这里会和服务端内部的 SSL_CTX 打架，进程直接 abort（下面第四节详述）。改法是把这两步放进 `queuemutex`：

```cpp
{
    std::lock_guard<std::mutex> lock(queuemutex);
    CloseConnection(conn);                 // 内部 delete + connectioncnt--
    conn = CreateConnection(TempConnect);  // 内部 connectioncnt++
}
```

- 同样地，`EndTx` 里 `handle.reset()` 也必须放在锁外——它可能是最后一份引用，析构会触发 `Guard → ReConnection`，那一步要拿 `queuemutex` 还要 `Ping`（一次网络往返）。放在锁内等于把一次 ping 的耗时算进 `txMutex` 的持锁时间。

```cpp
{
    std::lock_guard<std::mutex> lock(txMutex);
    handle = it->second;
    txTable.erase(it);
}
handle.reset();     // 锁外释放
```

## 锁顺序

- 池里有两把锁：`txMutex`（事务表）和 `queuemutex`（连接队列）。约定顺序是：

```
txMutex → queuemutex
```

- 反向会死锁。监控线程原来是这样调回收的：

```cpp
lock.unlock();                  // 先让出 queuemutex
ReapExpiredTx();
lock.lock();
```

- 如果不 unlock 直接调，就变成 `queuemutex → txMutex`，和约定反着来。

## `unlock` / `lock` 之后必须重查条件

```cpp
lock.unlock();
const std::size_t reaped = ReapExpiredTx();
lock.lock();

if (stop) break;   // 让锁那几百微秒里，shutdown() 可能已经置位
```

- `std::unique_lock` 手动解锁不是原子操作，中间这段时间别的线程可以改状态。

## 不要在自动变量上显式调析构

- 想让 `lock_guard` 提前放锁，第一版写成了：

```cpp
std::lock_guard<std::mutex> lock(handle->mtx);
...
lock.~lock_guard();          // 错
sqlpool->EndTx(in.tx_id());
```

- `lock_guard` 是**自动变量**，作用域结束时会再析构一次 → 双重解锁 → 未定义行为。手动调析构只对**动态分配**（placement new）出来的对象成立。

- 正确做法是用一对花括号限定作用域：

```cpp
{
    std::lock_guard<std::mutex> lock(handle->mtx);
    ... 成功路径在这里 return ...
}   // 锁在这里自动释放
sqlpool->EndTx(in.tx_id());
```

- 如果确实要"中途放锁再重新加"，用 `std::unique_lock` 的 `unlock()` / `lock()`——那是它提供的接口，不是靠析构。

## 监控快照要一次加锁拿全

- 池状态有 total / idle / waiting 三个数。分三次调用会拿到互相矛盾的组合：

```
connectioncnt = 150
connectionque.size() = 160     ← 不可能，但两次加锁之间连接被归还了
```

- 所以收成一个结构 + 一次加锁：

```cpp
struct Snapshot
{
    int total = 0;           ///< 连接总数（含借出的）
    int idle = 0;            ///< 空闲连接数
    std::size_t waiting = 0; ///< 等待队列长度
};

Snapshot GetSnapshot()
{
    std::lock_guard<std::mutex> lock(queuemutex);

    Snapshot snap;
    snap.total = connectioncnt;
    snap.idle = static_cast<int>(connectionque.size());
    snap.waiting = wait_queue.size();
    return snap;
}
```

# 异常与进程存活

## 异常逃出线程函数 = `std::terminate`

- 线程池任务原来长这样：

```cpp
threadPool->enques([session, msg_id, msg]() { session->reply(msg_id, router(msg)); });
```

- `router()` 里任何未捕获异常都会穿过 worker 线程。C++ 标准规定：**异常离开线程函数 → `std::terminate` → 进程直接 abort**，默认连一行日志都不留。

- 表现就是"服务在压力下无声消失"，客户端那边一堆 `ConnectionAbortedError(10053)`。

- 改法是把整个任务体包起来：

```cpp
std::string reply;
try
{
    reply = router(msg);
}
catch (const std::exception& e)
{
    outErr(std::string("router 抛出异常：") + e.what());
    reply = makeErrorReply(msg_id, RPC_STATUS_INTERNAL, "INTERNAL", e.what());
}
catch (...) { /* ... */ }
session->reply(msg_id, reply);
```

- 注意 `catch (const std::exception&)` **必须按引用**——按值捕获会把 `runtime_error` 切成 `std::exception`，`what()` 就只剩 `"std::exception"`。

## `std::set_terminate`

- 兜底用，把"静默 abort"变成"先打日志再 abort"：

```cpp
std::set_terminate([]()
{
    try
    {
        if (auto eptr = std::current_exception()) { std::rethrow_exception(eptr); }
    }
    catch (const std::exception& e) { Utils::Out::outErr(std::string("未捕获异常：") + e.what()); }
    catch (...) { Utils::Out::outErr("未捕获异常（非 std::exception）"); }
    std::abort();
});
```

- `std::current_exception()` 拿到的是"导致 terminate 的那个异常"的 `exception_ptr`，`rethrow_exception` 之后才能 `catch` 出 `what()`。

## Windows 的结构化异常

- `set_terminate` 只管 C++ 异常。访问越界（`0xC0000005`）、栈溢出（`0xC00000FD`）这类 SEH 异常得用：

```cpp
#include <windows.h>

static LONG WINAPI onUnhandledException(EXCEPTION_POINTERS* info)
{
    const DWORD code = info->ExceptionRecord->ExceptionCode;
    char buf[64];
    std::snprintf(buf, sizeof(buf), "0x%08lX @ %p", (unsigned long)code, info->ExceptionRecord->ExceptionAddress);
    Utils::Out::outErr(std::string("未处理的系统异常，code=") + buf);
    return EXCEPTION_EXECUTE_HANDLER;
}

SetUnhandledExceptionFilter(onUnhandledException);
```

- 异常码能直接区分是内存问题还是别的：`0xC0000005` = 访问越界，`0xC00000FD` = 栈溢出。

# MySQL / 连接池

## 事务状态属于连接

- `START TRANSACTION` 只对当前连接生效，所以 `inTx` / `txId` / `txOwner` / `txDeadline` 四个字段直接挂在 `Connection` 上：

```cpp
bool BeginTransaction(const std::string& id, std::int32_t owner, int ttlSec);
bool CommitTransaction();
bool RollbackTransaction();
void ExtendTransaction(int ttlSec);
bool TxExpired() const;
```

- 好处是能给池加一道防线——归还时发现连接还在事务里，直接强制回滚：

```cpp
if (conn->InTransaction())
{
    Utils::Out::outErr("归还了仍在事务中的连接，强制回滚：" + conn->TxId());
    conn->RollbackTransaction();
}
```

- 没有这一条，一旦有人漏了 `COMMIT`，那条连接带着未提交事务回到池里，被下一个线程借走后所有写操作都会"继承"前一个事务。

- 但光有状态不够，还需要一张 `tx_id → 连接` 的表，因为 9102/9103/9104 只带 `tx_id`。表里必须存 `Guard`（所有权），只存 `Connection*` 的话连接会被下一个请求借走。

## `ROLLBACK` 失败要断连

- 提交失败保留状态（调用方还能回滚），**回滚失败则直接掐掉连接**：

```cpp
else
{
    SetError(mysql_errno(conn), mysql_error(conn));
    Utils::Out::outErr(mysql_error(conn));

    // 回滚失败：连接的事务状态已经不可信，直接掐掉
    DisConnect();
}
```

- 因为 `ROLLBACK` 都失败，通常意味着连接已经断了。`DisConnect()` 之后池在归还时 `Ping` 必然失败 → 走既有的销毁重建分支，一条状态未知的连接绝不会回到队列。

## 死锁 1213 会回滚整个事务

- 大多数语句错误（1064 语法错、1062 唯一键冲突）**不会**回滚事务，事务还开着。但 **1213（死锁）是例外**——MySQL 会把整个事务回滚掉，而我们这边的 `inTx` 还是 `true`。

- 这不要紧：后续 `COMMIT` 是空事务提交、`ROLLBACK` 是空事务回滚，都不会出错。属于"状态允许短暂不一致，但操作幂等"。

## 事务 TTL：过期要在访问时判定

- 池的巡检线程间隔是 `max(5, min(60, connect_timemax / 3))`，`timemax=60` 时就是 **20 秒一次**。也就是说即使 TTL 只有 2 秒，事务也要等最多 20 秒才会被 `ReapExpiredTx` 回收。

- 所以过期必须在**访问路径**上判，巡检只负责清理没人再访问的僵尸事务：

```cpp
if (!conn->InTransaction() || conn->TxExpired())
{
    if (conn->InTransaction()) { conn->RollbackTransaction(); }   // 就地回滚
    // 放锁后再 EndTx
    return FAILED_PRECONDITION;
}
```

- 提交和回滚对"已过期"的语义不同：

| 请求 | 事务已过期 | 返回 |
| --- | --- | --- |
| COMMIT | 只回滚 | `FAILED_PRECONDITION` |
| ROLLBACK | 只回滚 | `OK`（调用方本来就想撤销） |

- TTL 做成环境变量，测试才验得了：

```cpp
static int txTtlSec = 30;

if (const char* v = std::getenv("DBPOOL_TX_TTL"))
{
    const int sec = std::atoi(v);
    if (sec > 0) { txTtlSec = sec; }
}
```

- 测试端：开事务 → 睡 2.5 秒 → 再发 TxSql。被拒说明 TTL 生效；还能执行说明 TTL 比 2.5 秒长，如实标成"无法验证"，不硬判失败。

## `OpenSSL internal error: refcount error`

- 压测时服务端直接 abort，日志是：

```
ssl\ssl_lib.c:1432: OpenSSL internal error: refcount error
```

- libmysql 内部**共用同一个 `SSL_CTX`**。当 A 线程 `mysql_close` 把引用计数减到 0 并释放，B 线程同时在 `mysql_real_connect` 里拿它做握手，计数就被打坏了。

- 根因就是上面那个"锁外 `delete conn` + `CreateConnection`"。锁住之后解决。

## 连接计数必须配对

- 原来 `delete conn` 后面没有递减 `connectioncnt`，而 `CreateConnection` 会 `++`。于是**每回收一次连接，计数就虚高 1**。跑久了会出现：

```
connectioncnt = 200（已达上限）
connectionque.size() = 0（其实是空的）
```

- `GetConnection` 判断 `connectioncnt < max` 不成立、队列又空 → 直接返回 `nullptr` → 业务侧一直 `RESOURCE_EXHAUSTED`，重启才能恢复。改用 `CloseConnection`（内部 `delete` + `--`）配对。

## 响应超过 1 MiB：截断，别静默丢包

- 一帧最大 1 MiB，超过之后连接层会**静默丢弃**——调用方永远等不到回包，只能超时。这是最坏的失败方式。

- 留 64KB 给 RpcResponse 骨架（head/code/detail/列名），其余给数据行：

```cpp
static constexpr std::size_t kResponseBudget = 1024 * 1024 - 64 * 1024;
```

- 每行先在栈上拼好，量出字节数，放得下才追加：

```cpp
std::size_t used = out.ByteSizeLong();     // 列名骨架已占用

while (MYSQL_ROW row = mysql_fetch_row(res))
{
    tzb::dbpool::v1::SqlRow one;
    for (...) { one.add_values()->... }

    const std::size_t rowSize = one.ByteSizeLong();
    if (used + rowSize > kResponseBudget)
    {
        out.set_truncated(true);           // 明确告诉调用方被截断了
        break;
    }

    out.add_rows()->Swap(&one);            // 放得下才追加，不会出现"半行"
    used += rowSize;
}
```

- 两个细节：

  - **先在栈上拼再 `Swap`**：直接往 `add_rows()` 里填的话，截断时表里已经挂了一行半成品。
  - **`used` 自己累加**：每行调一次 `out.ByteSizeLong()` 是全量序列化扫描，1000 行就是 O(n²)，一次查询要多扫近 1GB 数据。

- 语义上选"截断 + `truncated=true`"而不是报错：proto 里的 `truncated` 字段就是为这个设计的，客户端看到就知道该缩小查询，不用拿错误码去猜。

- `makeReply` 再兜一道，防止别的路径把包撑爆：

```cpp
if (out.size() > kResponseBudget)
{
    outErr("响应 " + std::to_string(out.size()) + " 字节超过帧上限，已丢弃（调用方会超时）");
    return std::string();
}
```

## 性能：日志是隐形瓶颈

- 压测 2000 条并发请求，吞吐只有 173 req/s，p50 5.4 秒。算一下：

```
每条 SQL 打 5 行日志 × 2000 请求 = 10000 行
墙钟 10.9 秒 ÷ 10000 行 ≈ 1.1ms / 行
→ 单请求光日志就要 5.5ms
→ 理论上限 = 1 ÷ 5.5ms ≈ 182 req/s    （实测 173，吻合）
```

- 控制台同步 I/O 把 200 个线程串行化了，SQL 本身可能只花了 0.2ms（本地环回）。

- **结论**：热路径日志默认关掉，用环境变量控制。

```cpp
inline bool verboseLog = false;   // DBPOOL_VERBOSE=1 时打开
if (verboseLog) { Utils::Out::outMsg("获取到连接！"); }
```

`outErr` 保留——错误日志是低频的，而且是排障的唯一线索。

# 超时控制

## 优化器提示只对 SELECT 生效

- 想让一条 SQL 最多跑 N 毫秒，最省事的办法是插优化器提示：

```sql
SELECT /*+ MAX_EXECUTION_TIME(200) */ SLEEP(1.5) AS v
```

- 超时后 MySQL 报 `errno 3024`，映射成 `DEADLINE_EXCEEDED` 即可：

```cpp
case 3024: // 执行时间超过 MAX_EXECUTION_TIME
case 1317: // 查询被 KILL
    return RPC_STATUS_DEADLINE_EXCEEDED;
```

- 它**只对只读 SELECT 生效**，`UPDATE` / `DELETE` 不吃这个提示。DML 的超时得另开一条连接 `KILL QUERY <id>`，代价大得多：多借一条连接、要定时器、要记 `mysql_thread_id`、杀完还要清理连接状态。

- 参数要 clamp：默认 1000，最大 5000。

```cpp
const std::int32_t ms = (timeoutMs <= 0) ? 1000 : (timeoutMs > 5000 ? 5000 : timeoutMs);
```

## 提示必须插在关键字正后面

- 写在别处 MySQL 会直接忽略，不报错也不生效。所以需要知道"首关键字在哪结束"：

```cpp
static std::string firstKeyword(const std::string& sql, std::size_t* endPos = nullptr);
```

- 加一个**带默认值的输出参数**，原有调用点一行都不用改；需要位置的调用方传 `&endPos` 即可：

```cpp
std::size_t kwEnd = 0;
if (firstKeyword(sql, &kwEnd) != "SELECT") { return; }

sql.insert(kwEnd, " /*+ MAX_EXECUTION_TIME(" + std::to_string(ms) + ") */");
```

- 前导空行和注释不用自己处理，`firstKeyword` 已经跳过：

```
-- 注释
SELECT 1     →  kwEnd 指向 "SELECT" 后面的位置
```

- 同一个入口既能"给默认值"又能"顺带回填"，比再加一个 `firstKeywordEnd()` 函数干净，也避免两处跳过注释的逻辑各写一遍。

## Windows 路径写在字符串里

```
SyntaxError: (unicode error) 'unicodeescape' codec can't decode bytes in position 3488-3489:
truncated \xXX escape
```

- docstring 里写了 `--report-md D:\x.md`，`\x` 是十六进制转义，后面没跟两位十六进制 → 直接语法错。

- 更坑的是 `D:\tmp`——`\t` 是合法转义（Tab），**不报错**，字符串悄悄变成 `D:` + Tab + `mp`。

- 三种改法：

```python
r""" ... D:\x.md ... """   # raw string，反斜杠不转义
""" ... D:\\x.md ... """   # 手动双写，漏一个就炸
""" ... D:/x.md ... """    # 正斜杠，Windows 的 open() 也认
```

- 命令行传参不受影响：`--log D:\tmp\a.log` 是 shell 把字符原样交给 `sys.argv`，Python 不做转义解析。

## 事务验证必须换连接

- 验证"回滚是否真的生效"，查询**不能用事务自己的连接**：

```python
# 错：事务内自查，永远查得到（同一连接可见未提交数据）
c.call_tx_sql(tx, "SELECT id FROM dict_item WHERE code = ?", ...)

# 对：走 9100，池会借另一条连接
c.call_sql("SELECT id FROM dict_item WHERE code = ?", ...)
```

- 用 9102 自查的话，回滚了也能查到，这个用例就白写了。

# 其他小点

- **测试报告按时间戳命名**：`功能实现清单_20261101_193030.md`，`%Y%m%d_%H%M%S` 保证按文件名排序就是时间线。
- **接口抽取得分层**：`validateSql`（规则，两处必须一致）/ `executeOn`（层，绑定+执行+解析）/ `finishTx`（编排，提交与回滚共用）。规则类代码最怕只改一处。
- **`std::atomic<uint64_t>` 生成 ID**：`++txSeq` 原子自增，再拼上 `steady_clock` 毫秒，单进程内唯一。
