# io_context 生命周期：dbpool 启动就崩

## 现象

```
[SQL][INFO] 2026-10-31 19:54:58 服务器对象初始化完成
[SQL][ERROR]2026-10-31 19:54:59 网络线程出现错误?????4? [system:6]
[SQL][INFO] 2026-10-31 19:55:18 开始检查是否有已经空闲的额外连接！   ← 进程还活着
```

三个关键点：

- `system:6` 是 Windows 的 `ERROR_INVALID_HANDLE`（句柄无效），不是在 `mysql_*` 里报的，是在 `io.run()` 里抛出来的
- **进程没死**：主线程还阻塞在 `waitExit()`，连接池的监控线程还在每 20 秒打一次日志
- 但 9011 / 9012 **永远不 accept**，客户端连上就断 → 测试脚本一条都跑不通

看到 `[system:6]` + "进程还活着但端口不响应"，第一反应就应该是：**有对象被提前销毁了，而另一个线程还在用它**。

## 先排除一个猜测：start() 和 run() 的先后

一开始怀疑是 `io.run()` 和 `server->start()` 的先后关系。顺序确实是敏感的，但**这次代码是对的**：

```cpp
server->start();                 // 先注册异步 accept
IO_Context = std::thread([&io]() { io.run(); });   // 再驱动事件循环
```

- `start()` 只负责把异步操作挂到 `io_context` 上，本身不阻塞
- `io.run()` 才是驱动它们的地方
- 反过来写（先 run 后 start）才是错的：`run()` 发现没有待处理的工作，会**立刻返回**

所以问题不在顺序，在**生命周期**：`runIOContext` 一返回，它里面的对象就没了，而线程还在跑。

## 根因一：io_context 是局部变量，却被线程按引用捕获

```cpp
void runIOContext(int port, std::thread& IO_Context,
                  std::shared_ptr<Net::Server::Server> server,      // ← 也是错的，见根因二
                  std::shared_ptr<Net::Server::HandleFunction> handler)
{
    boost::asio::io_context io;                                     // ← 栈上
    boost::asio::ip::tcp::endpoint ep(boost::asio::ip::tcp::v4(), port);
    server = std::make_shared<Net::Server::Server>(io, ep, handler, ...);
    server->start();

    IO_Context = std::thread([&io]() { io.run(); });                 // ← 引用捕获
}                                                                    // ← 函数返回：io 析构
```

`std::thread` 构造时会把 lambda **复制**一份到新线程，但复制的是 **lambda**，里面装的还是 `&io` —— 一个指向函数栈帧的地址。

而且 `boost::asio::io_context` **既不可拷贝也不可移动**，所以根本没法"把对象搬进线程"：

```cpp
std::thread([io = std::move(io)] { ... });   // ❌ 编译不过，io_context 没有移动构造
```

### 时间线

```
t0   runIOContext 进入，io 构造在栈上
t1   server 创建 + start()，注册异步 accept
t2   std::thread 构造，lambda 复制进新线程（里面只有一个 &io）
t3   新线程跑起来，io.run()  —— 此刻 io 还活着 ✅
t4   runIOContext 返回
       ├─ 栈帧销毁 → io.~io_context() → 内部 IOCP 句柄被关掉
       └─ server（局部副本）析构 → 关闭 acceptor、销毁会话
t5   新线程还在 io.run() 里，下一次事件循环碰到已关闭的句柄
       └─ ERROR_INVALID_HANDLE [system:6]  💥
```

`t4` 和 `t5` 之间就是日志里那 **1 秒**的间隔：线程在 `t3` 进去后先阻塞等事件，等下一次事件（或内部定时器）触发时才访问已经关掉的句柄。所以不是"立刻崩"，而是"晚一秒崩"，很容易被误判成别的问题。

**析构发生在主线程，它不会等另一个线程从 `io.run()` 里出来。** 这就是"悬垂引用"的定义 —— 对象已经没了，指针还指着它。

## 根因二：shared_ptr 按值传参，调用方拿到的是空指针

```cpp
void runIOContext(int port, std::thread& IO_Context,
                  std::shared_ptr<Net::Server::Server> server,     // ← 按值
                  ...)
{
    server = std::make_shared<Net::Server::Server>(io, ep, handler, ...);
}

// main
std::shared_ptr<Net::Server::Server> microservice_net = nullptr;
runIOContext(port, thread, microservice_net, handler);
//                              ↑ 传的是这个 shared_ptr 的副本
```

`weak_ms_net = microservice_net;` 存进去的是一个空 `weak_ptr`，退出回调里 `if (auto s = weak_ms_net.lock())` 永远进不去，`microservice_net->stop()` 直接空指针。

两个误解要拆开：

- "传 shared_ptr 就会共享所有权" —— 共享的是**这个指针副本**在函数执行期间的那一小段
- "函数里 make_shared 之后 main 能拿到" —— **拿不到**，除非参数是引用（出参）或函数返回它

按值传参时，函数结束那一刻副本销毁，引用计数归零，`Server` 当场析构 —— 而它的 `~Server()` 恰好会去关 acceptor、关所有会话，正好落在 `io.run()` 还在跑的时候。

## 根因三：weak_ptr 赋错了变量

```cpp
runIOContext(listenManagePort, ManageIOContext, microservice_Manage, ...);
weak_ms_net = weak_Manage;      // ← 应该是 weak_Manage = microservice_Manage;
```

复制粘贴的经典。后果：管理口的 `weak_ptr` 永远是空，Ctrl+C 时 9012 停不掉。

## 为什么 io_context 和 server 必须分开持有

这是这次最值得记的一条。三个约束叠在一起，决定了它俩的关系：

1. **`Server` 内部存的是 `io_context&`，不是 `shared_ptr`**
   `Server(boost::asio::io_context& io, ...)` —— 它只借用，不拥有。
2. **`~Server()` 会向 `io_context` post 关闭任务**
   `~Server()` → `stop()` → `ioc.post(...)` 关 acceptor / 关会话。
   所以 **`io` 必须比 `server` 活得久**，否则析构阶段又踩一次空。
3. **`io.run()` 是阻塞的**
   它要一直跑到没有待处理工作为止。如果 `runIOContext` 里 `join()`，`main` 就卡死在启动函数里，永远到不了 `waitExit()`，Ctrl+C 也没人处理。

于是只能这样：

| 对象 | 谁持有 | 为什么 |
| --- | --- | --- |
| `io_context` | 线程 **+** `main`（`shared_ptr`） | 线程要用它跑 `run()`；`main` 要保证它在 `server` 析构时还在 |
| `Server` | `main`（`shared_ptr` 出参） | 退出时要 `stop()`；`main` 必须在启动函数返回后仍持有它 |

**不能只让线程持有 `io`**：

```
join() 之后线程结束 → io 引用计数归零 → 销毁
main: microservice_net.reset() → ~Server() → stop() → 向 io_context post(...)
                                                        ↑ 已经没了
```

## 修复

```cpp
// Worker.h
void runIOContext(const int port, std::thread& IO_Context,
                  std::shared_ptr<boost::asio::io_context>& IO,        // 出参：交给调用方持有
                  std::shared_ptr<Net::Server::Server>& server,        // 出参：必须传引用
                  std::shared_ptr<Net::Server::HandleFunction> handle);
```

```cpp
// Worker.cpp
void runIOContext(const int port, std::thread& IO_Context,
                  std::shared_ptr<boost::asio::io_context>& IO,
                  std::shared_ptr<Net::Server::Server>& server,
                  std::shared_ptr<Net::Server::HandleFunction> handler)
{
    IO = std::make_shared<boost::asio::io_context>();
    boost::asio::ip::tcp::endpoint ep(boost::asio::ip::tcp::v4(), port);

    server = std::make_shared<Net::Server::Server>(*IO, ep, handler, 60, 60, 1024 * 1024 * 100, 60, 200);
    server->start();

    auto io = IO;                       // 线程也持有一份
    IO_Context = std::thread([io, server]() { io->run(); });
}
```

```cpp
// main.cpp
std::shared_ptr<boost::asio::io_context> ioNet;      // ← 声明在 server 之前
std::shared_ptr<boost::asio::io_context> ioManage;

std::shared_ptr<Net::Server::Server> microservice_net = nullptr;
runIOContext(listenServerPort, serverIOContext, ioNet, microservice_net, handler);
```

两个细节：

- 线程捕获 `[io, server]`：lambda 的捕获**按声明顺序构造、按逆序析构**，所以线程结束时 `server` 先销毁、`io` 后销毁，正好满足"io 比 server 活得久"
- `main` 里 `ioNet` 声明在 `microservice_net` **之前**：局部变量析构顺序与声明**相反**，所以 server 先析构、io 后析构 —— 同一个保证，在另一个作用域里又做了一遍

## 顺序 和 生命周期，是两条独立的规则

| 规则 | 内容 | 这次犯了吗 |
| --- | --- | --- |
| **顺序** | `start()` 必须在 `run()` 之前；`stop()` 之后 `run()` 才会返回 | 没犯 |
| **生命周期** | 线程访问的每一个对象，都必须比这个线程活得久 | 犯了两个（io 和 server） |

把这两条混在一起，就会出现"顺序明明是通的，为什么还是崩"的情况。

## 顺带修掉的两个"静默失败"

```cpp
// 之前：启动失败什么都不说
catch (...)
{
}

// 现在
catch (...)
{
    Utils::Out::outErr("服务器启动失败（未知异常）");
    return -1;
}
```

空 `catch` 是 bug 温床。这次之所以绕了一圈，部分原因就是"启动阶段出问题也看不出来"。

## 排查这类问题的手法

1. **`system:N` 去查 Windows System Error Codes**
   `6 = ERROR_INVALID_HANDLE`、`995 = ERROR_OPERATION_ABORTED`、`1236 = ERROR_CONNECTION_ABORTED`
   凡是 `io.run()` 里抛 `system:N`，先怀疑"对象被提前销毁"。
2. **看日志时间线**
   `初始化完成` → 1 秒后 `网络线程出现错误` → 说明错误发生在**函数返回之后**，不是初始化本身。
3. **`netstat -ano | findstr 9011`**
   进程活着但端口不是 `LISTENING`，就是 accept 循环根本没在跑。
4. **进程活着 ≠ 服务活着**
   IO 线程死了，主线程还在 `waitExit()`，监控线程还在打日志 —— 日志照刷，端口全哑。

## 经验

1. **线程只搬走"执行流"，不搬走"数据"**。`std::thread` 复制的是 callable，里面的引用还是引用。
2. **局部变量 + `[&x]` 捕获 = 悬垂**。只要线程活得比函数长，就一定出事。
3. **`shared_ptr` 当出参必须用引用**（`shared_ptr<T>&`），按值传只是"函数执行期间共享"，不是"交接所有权"。
4. **用析构顺序表达依赖关系**：`io` 声明在 `server` 前面，就是在说"我比你活得久"。
5. **别写空 `catch (...)`**，尤其是启动路径。
