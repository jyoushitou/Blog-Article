# 网关的分层与数据流

## 一次请求的完整路径

```
浏览器
  │  HTTP/1.1
  ▼
[9001 业务口] ──┐
                ├─ HttpServer 回调（IO 线程，绝不阻塞）
[9002 管理口] ──┘        │
                         ├─ 拷贝一份 Url（请求上下文）
                         ├─ 投递到主线程池（4096）
                         ▼
              线程池 worker
                 ├─ 认证：验 JWT → Actor
                 ├─ 本机路由：/health /version /telemetry/errors /me/workbench
                 ├─ 路由匹配：方法+路径 → 命令号；最长前缀 → 服务号
                 ├─ 鉴权：登录要求 + 权限码（A-05 缓存 5min）
                 ├─ 限流：上传 5/分/账号、上报 20/分/会话
                 ├─ 请求整形：refresh Cookie 注入、幂等键透传
                 ├─ JSON → protobuf（按命令号查描述符）
                 ├─ callService：组 RpcRequest → TCP → 阻塞等回包
                 ├─ 回包 → 状态码映射 → protobuf → JSON
                 ├─ BFF 补字段（队伍成员姓名）
                 └─ 回包（httpAsyncReplay）
```

两条铁律贯穿全部代码：

- **IO 线程只做投递**。Net 库的回调跑在 `io_context` 的线程上，那里一旦阻塞，同一条 `io_context` 上的所有连接一起卡死。
- **状态码用返回值表达**。响应体写回 `Url.body`（复用库的类型），不自定义结果结构体。

## 为什么状态码不放 Url 里

`Net::Server::HttpServer::Url` 是**请求上下文**：`method` / `target` / `headers` / `body` / `seq`，没有状态码字段。一开始想加个自定义 `HttpResult`，后来发现完全没必要：

```cpp
// 状态码走返回值，body 原地替换成响应体
boost::beast::http::status router(Net::Server::HttpServer::Url &url)
{
    // ...
    url.body = R"({"ok":true})";
    return boost::beast::http::status::ok;
}
```

好处是调用点只有一句 `st = route(req)`，没有第二个结构体要在各层之间搬运。

## 路由表：5 元组，不搞类

103 条业务接口，一条一个 `std::tuple`：

```cpp
// 命令号 / 方法 / 路径模板 / 请求消息名 / 响应消息名
using Route = std::tuple<int, boost::beast::http::verb, std::string_view,
                         std::string_view, std::string_view>;
```

拆成 7 个文件（`Router_A.cpp` … `Router_J.cpp`，按业务域），每个文件一张表：

```cpp
const std::vector<Route> &routesTeam()
{
    static const std::vector<Route> table = {
        {4001, verb::get,    "/api/v1/teams/{team_id}", "tzb.team.v1.GetTeamRequest", "tzb.team.v1.GetTeamResponse"},
        {4011, verb::get,    "/api/v1/teams/mine",       "tzb.team.v1.ListMyTeamsRequest", "tzb.team.v1.ListMyTeamsResponse"},
        // ...
    };
    return table;
}
```

**消息类型也放在表里**——这样"接口 → 命令号 → protobuf 类型"三者永远在一行内对齐，加接口不用改第二个地方。

## 两轮匹配：静态优先于通配

`/api/v1/teams/mine` 和 `/api/v1/teams/{team_id}` 会长在同一棵前缀上。做法是先查静态表，再查通配：

```cpp
// 不用 std::span：VS 的 IntelliSense 跟着引用工程的 C++17 走，会报"没有成员 span"
const Route *matchPath(const std::vector<Route> &routes, verb method, std::string_view path)
{
    // 第一轮：完全相等（命中最多）
    // 第二轮：`{param}` 段按单段通配
}
```

`/api/v1/teams/mine` 在第一轮就命中 `4011`，不会掉进 `/api/v1/teams/{team_id}` 被当成 `team_id = "mine"`。

# HTTP → 内部消息：协议层

## 12 字节头

网关和微服务之间的 TCP 有自己的帧格式，**8 字节 msg_id + 4 字节长度**，都按大端：

```
+----------------+----------------+---------------------------+
|   msg_id (8B)  |  length (4B)   |  payload (length 字节)     |
+----------------+----------------+---------------------------+
        大端              大端         protobuf 序列化后的字节
```

三个硬约束（都踩过）：

- `length` 必须是 **1 ~ 1 MiB**。回 0 字节会被库判成非法并**直接断开连接**；
- `msg_id` 是"请求身份证"，回包必须**原样回显**；
- `msg_id = 0` 是保留值：连接建立后框架自动发一条 check connection，服务端按同号回一条，网关收到才算"链路真的通了"。

第三条很重要：**TCP 三次握手成功 != 对端业务可用**。所以"就绪"不能拿 connect 成功判定，必须等 check connection 回来：

```cpp
if (id == Net::CheckConnectionReturnMsgId)
{
    // 只有收到它才置"就绪"
    runings[index]->exchange(true, std::memory_order_acq_rel);
    return;
}
```

`exchange` 的返回值用来判断"是不是第一次置位"，避免同一条连接重复打日志。日志刷屏在压测时非常致命——`Utils::Out::outMsg` 是带锁的。

## 等待槽：同步语义 + 异步框架

`callService` 对外是**同步**的（worker 阻塞等结果），但底层 TCP 是异步的。中间靠一张"等待槽"表：

```cpp
struct PendingRequest
{
    std::mutex mtx;
    std::condition_variable cv;
    bool done = false;
    tzb::common::v1::RpcResponse resp;
};
```

流程：

```
worker 线程                              客户端 IO 线程（每个微服务一条）
-----------                              --------------------------------
① ++msg_id（原子）生成身份证
② 组 RpcRequest（command 决定服务端分发）
③ pendingRequests[id] = 槽
④ client->toSend(id, body)  ───────────▶ 发到微服务
⑤ 在 槽->cv 上等（≤ rpcTimeoutMs）        ⑥ 服务端用同一个 msg_id 回 RpcResponse
                                          ⑦ 收包回调 → handleWork(msg)
                                          ⑧ 按 head.msg_id 找回槽
⑨ 被唤醒，取走信封        ◀──────────────  ⑨ 结果存进槽 → notify_one
```

两个细节：

- **槽的摘除要早**。`handleWork` 里找到槽之后先 `erase` 再唤醒，保证一条回包只交一次。
- **找不到槽不是错误**。那是"迟到回包"——worker 早就超时返回了，这条回包丢掉即可。**绝不能因为收到迟到回包就去关连接**，否则一条慢回包能把整条链路拆掉。

## 超时后的清理

超时路径必须把槽删掉，否则表会随超时请求无限增长：

```cpp
std::unique_lock<std::mutex> lock(slot->mtx);
if (!slot->cv.wait_for(lock, std::chrono::milliseconds(rpcTimeoutMs), [&] { return slot->done; }))
{
    // 超时：摘槽 → 返回 504
    pendingRequests.erase(id);
    return gatewayUnavailable(...);
}
```

# protobuf ↔ JSON：不写死类型

## 描述符池动态查类型

103 条接口如果每条都写一遍 `GetRequest()` / `SetResponse()`，代码量爆炸。所以用**运行期查类型**：

```cpp
const google::protobuf::Descriptor *desc =
    google::protobuf::DescriptorPool::generated_pool()->FindMessageTypeByName(typeName); // "tzb.team.v1.GetTeamRequest"

const google::protobuf::Message *prototype =
    google::protobuf::MessageFactory::generated_factory()->GetPrototype(desc);

std::unique_ptr<google::protobuf::Message> msg(prototype->New());
```

`typeName` 就来自路由表的第 4、5 个字段。这样加接口只需要在表里加一行，JSON 转换代码一行都不用动。

## `/WHOLEARCHIVE`：静态库的注册表会被丢掉

第一次跑起来全部接口返回 400，日志是"找不到消息类型"。

根因：protobuf 的 `descriptor()` 靠**静态初始化时向 `generated_pool` 注册**。链接器看到 `*.pb.cc` 里的符号没被引用，就把整个目标文件丢了——注册代码自然也没执行。

```cmake
# MSVC
target_link_options(GateWay PRIVATE "/WHOLEARCHIVE:$<TARGET_FILE:GateWayProto>")
# GCC/Clang
target_link_options(GateWay PRIVATE "--whole-archive")
```

## JSON 里的 int64 是字符串

这是最容易静默出错的地方。protobuf 的 JSON 映射规定 **int64/uint64 输出为字符串**：

```json
{ "account_id": "1843920517801234432" }
```

网关的 BFF 要按 `account_id` 给队伍成员补姓名，一开始这么写的：

```cpp
if (value.is_int64()) { id = value.as_int64(); }   // 永远不成立
```

于是补姓名永远失败，而且**不报错**。修法是接受两种形态：

```cpp
std::int64_t readInt64(const boost::json::value &value)
{
    if (value.is_int64())  { return value.as_int64(); }
    if (value.is_string()) { return std::stoll(std::string(value.as_string())); }  // 数字字符串
    throw std::runtime_error("不是整数");
}
```

## 保留原始字段名

```cpp
google::protobuf::util::JsonPrintOptions options;
options.preserve_proto_field_names = true;   // account_id 而不是 accountId
options.always_print_primitive_fields = false; // 空 repeated 字段不输出，响应体更小
```

不开 `preserve_proto_field_names` 的话，protobuf 默认转驼峰，前端拿到的字段名和文档对不上。

# JWT：RS256 本地验签

## 为什么不引第三方库

只需要"验签"（不签发），OpenSSL 的 EVP 接口就够了，省掉 jsonwebtoken 那类库的依赖和编译麻烦。

## 验签流程

```cpp
// 1) 拆三段：header.payload.signature（base64url，无 padding）
// 2) header 里必须是 {"alg":"RS256","typ":"JWT"}
// 3) 用公钥验签：EVP_DigestVerifyInit(EVP_sha256) + EVP_DigestVerify
EVP_PKEY *key = PEM_read_PUBKEY(fp, nullptr, nullptr, nullptr);
EVP_MD_CTX *ctx = EVP_MD_CTX_new();
EVP_DigestVerifyInit(ctx, nullptr, EVP_sha256(), nullptr, key);
EVP_DigestVerify(ctx, sig, sigLen, (const unsigned char *)signingInput, inputLen) == 1;
```

## claims 的校验顺序

**先验签，再验 claims**——顺序反了等于让攻击者用任意伪造的 payload 触发我们的解析逻辑。

```cpp
// 1) alg 必须是 RS256（拒绝 alg=none 和 HS256 降级攻击）
// 2) iss == "tzb-auth"
// 3) aud == "tzb-api"
// 4) typ == "access"（refresh 令牌不能当 access 用）
// 5) exp / nbf，允许 ±30s 时钟偏移
// 6) sub 必须是数字（账号 ID），转成 int64
```

`typ` 那条特别关键：同一套密钥签 access 和 refresh，不校验类型的话，**拿 refresh 令牌就能直接访问业务接口**，刷新流程等于白设计。

## Actor 注入与内部签名

验签通过后把身份塞进请求消息的 `Header.actor`：

```cpp
tzb::common::v1::Actor *actor = request.mutable_head()->mutable_actor();
actor->set_account_id(claims.accountId);
actor->set_user_type(claims.userType);
```

同时给内部调用加 HMAC 签名，防"绕过网关直接打微服务"：

```
Header.sign = HMAC-SHA256(key, service|goal|command|trace_id|timestamp_ms)
```

## Set-Cookie 的尴尬

refresh 令牌想放进 httpOnly Cookie，但库的 `httpAsyncReplay(seq, body, status)` **只有一个 body 参数**，设不了响应头。代码里留了个开关：

```cpp
#define GATEWAY_REPLY_HAS_HEADERS 0   // 库补上带响应头的重载后置 1
```

现在这条路径降级为"令牌仍在响应体里"，并打一条一次性警告——**不能默默降级**，否则上线才发现 httpOnly 流程没生效。

# 线程池：4096 + 256 的两池设计

## 为什么 HTTP 转消息需要 4096 个线程

`callService` 是**阻塞**的（等上游回包，最长 300ms）。这类任务的线程数要按"同时在途的请求数"给，不是按 CPU 核数给。按 CPU 给 16 个线程，16 路并发之后全部排队。

```cpp
inline std::size_t threadPoolSize = 4096;
```

代价是 4096 份栈地址空间（Windows 默认 1MB，按需提交），启动时一次性创建。

## 为什么并行扇出要另一个池（死锁推演）

BFF 工作台要扇出 3 个上游。第一版很自然地写成"投递到本池 + 等结果"：

```cpp
auto f = threadPool->enques(...);   // 子任务排进【同一个池】
f.get();                            // 等它跑完
```

推演一下最坏情况：

```
主池 4096 个 worker，全都在处理 /me/workbench
每个都卡在 f.get()，等自己的子任务
子任务排在同一个池的队列里，等一个空闲 worker
→ 没有空闲 worker → 永远等下去
```

这叫**线程饥饿死锁**（thread starvation deadlock）。修法不是加线程数，而是**让"等待方"和"被等待方"不在同一个池**：

```cpp
// 专用池：worker 只做 RPC，永远不会反过来等主池 → 成不了环
inline ThreadPool::ThreadPool *fanoutPool = nullptr;   // 256 线程
```

包装一层，顺便处理"池已停止"的退化：

```cpp
template <typename T>
std::future<T> runFanout(std::function<T()> task)
{
    if (fanoutPool != nullptr)
    {
        try { return fanoutPool->enques(task); }   // 传左值：抛异常时 task 仍有效
        catch (...) { /* 池已停止，走退化 */ }
    }
    return std::async(std::launch::deferred, std::move(task));  // get() 时在调用线程跑
}
```

实测（3 个依赖各 200ms）：串行 ≈600ms，并行 **209ms**。依赖全挂时也是并行超时，**316ms** 返回 200 + `degraded:true`，不是 900ms。

## 队列满 = 静默丢任务：三个 bug

线程池原实现里有两行：

```cpp
// 原来
if (maxWorkQueNum == workQueNum) { return retfuture; }   // 满了就……丢任务，但返回正常 future
std::atomic<int> workQueNum;                              // 没有初始化
```

三个问题叠在一起：

- **判满在锁外，且用 `==`**：和 `workQueNum++` 有竞态；计数一旦越过上限，`==` 永远不成立 → 判满彻底失效；
- **`workQueNum` 没初始化**：C++17 下 `std::atomic<int> x;` 不给初值，第一次入队读的是垃圾值；
- **丢任务却返回正常 future**：调用方 `get()` 永久阻塞，而且**根本没办法知道任务没执行**。

修法：

```cpp
// 1) 显式初始化
std::atomic<int> workQueNum{0};

// 2) 判满进锁、用 >=、满了抛异常
std::lock_guard<std::mutex> lock_mtx(this->mtx);
if (stop) throw std::runtime_error("error : ThreadPool on off");
if (workQueNum >= maxWorkQueNum) throw std::runtime_error("error : ThreadPool queue full");
```

"抛异常"比"静默丢弃"好，是因为**调用方终于能分辨了**。

## 网关侧的两道防线

即便线程池抛异常了，网关仍然要防"请求永远不回包"：

**① 入队前看积压，超阈值快速失败**

```cpp
if (threadPool->QueueSize() > maxPendingRequests)   // 2 万
{
    // 直接 503 OVERLOADED，不排队
}
```

4096 worker × 300ms ≈ 1.3 万/秒的排空速度，2 万积压≈1.5 秒延迟，再往后拒绝比继续排队合理。

**② 并行扇出带超时等**

```cpp
template <typename T>
bool waitFanout(std::future<T> &future, T &out, const int timeoutMs)
{
    if (future.wait_for(std::chrono::milliseconds(timeoutMs)) != std::future_status::ready)
    {
        return false;   // 任务可能被丢弃/卡住，按失败处理
    }
    try { out = future.get(); return true; } catch (...) { return false; }
}
```

**禁止直接 `future.get()`**——万一将来又出现"丢任务"，最坏是降级，而不是挂死一个 worker。

# io_context 生命周期三条铁律

## 铁律一：`Connect()` 必须早于 `run()`

重构连接代码时，我把顺序写成了"先起线程跑 `io.run()`，再 `Connect()`"，结果**所有微服务都连不上，而且不报错**。

原因：`io_context::run()` 在**没有待处理工作时立即返回**。线程先跑起来看到队列是空的，`run()` 直接退出；之后 `Connect()` 投递的异步操作永远没有线程去执行。

```cpp
// 正确顺序
client->Connect();                                        // 先投递
MSClient[index].iot = std::thread([&io] { io.run(); });   // 再起线程
```

这个 bug 最坑的地方是**没有任何错误日志**——连接请求发出去了，只是没人跑。

## 铁律二：`Client` 持有 `io_context&`，销毁时先 client 后 io

`Net::Client::Client` 的构造函数签名是 `Client(io_context &io, ...)`，它内部存的是**引用**。所以：

```cpp
// 错：先销毁 io_context，旧 client 还活着 → 悬空引用（UB）
ioContexts[index] = std::make_unique<io_context>();
MSClient[index].client = fresh;

// 对：先放掉旧 client，再换 io_context
oldClient.reset();
MSClient[index].client.reset();
ioContexts[index] = std::make_unique<io_context>();
```

重连时代价很直观：顺序错了，维护线程会**卡死**（不是崩溃），因为悬空引用踩到了别处内存。

## 铁律三：joinable 的 `std::thread` 被析构 = `std::terminate` = `abort()`

这就是那个 Debug 弹框：

```
Debug Error!
Program: ...\GateWay.exe
abort() has been called
```

`std::thread` 的析构函数有一条硬规定：**对象仍 joinable 时调用 `std::terminate`**。而 `std::terminate` 的默认行为就是 `abort()`。

网关里每个微服务连接都有一条 `iot` 线程，存在全局容器 `MSClient` 里。进程退出时：

```
静态析构 std::vector<ClientPtr>
  └─ 析构每个 ClientPtr
       └─ 析构 std::thread iot（仍 joinable）
            └─ std::terminate() → abort() → 弹框
```

触发路径有两个：**Ctrl+C** 和 **初始化失败**（后者更常见——没起微服务，5 秒后 `init()` 超时抛异常，`main` 返回 1，紧接着静态析构）。

修法是"退出前收干净"：

```cpp
void stopConnectionMS()
{
    // 1) 先在锁内取快照并请求关闭（stop 只是投递，不阻塞）
    { std::lock_guard lock(clientsMutex); for (auto &e : MSClient) if (e.client) e.client->stop(); }

    // 2) 停各自的 io_context，让 run() 返回
    for (auto &io : ioContexts) if (io) io->stop();

    // 3) join —— 不能持 clientsMutex：IO 线程的回调也要拿这把锁
    for (auto &e : MSClient) if (e.iot.joinable()) e.iot.join();

    // 4) 清容器：这是关键一步，清了才没有 joinable 线程留给静态析构
    { std::lock_guard lock(clientsMutex); MSClient.clear(); ioContexts.clear(); runings.clear(); toClient.clear(); }
}
```

而且**每个退出路径都要调**：init 失败、监听失败、正常收尾。

# 优雅退出：收尾必须写在信号回调里

## 反直觉的实测结果

第一版把收尾写在 `waitExit()` 之后：

```cpp
Utils::Exit::waitExit();          // 阻塞到收到信号
// ↓ 这些代码在 Ctrl+C 时【一次都没执行过】
gateWayIOContext.join();
threadPool->stopThread();
Utils::Out::outMsg("网关已退出");
```

日志证据：

```
22:16:16 收到退出信号，正在停止服务器...     ← 库的信号处理跑了
（之后没有任何日志，进程以 0xC000013A 结束）  ← main 的收尾从未跑到
```

`0xC000013A` 是 `STATUS_CONTROL_C_EXIT`。**信号处理链走完之后进程直接被系统终止**，`waitExit()` 之后的代码不保证执行——有时能返回（系统给了 5 秒窗口），有时来不及。这种"有时"最要命。

## 收尾塞进停止回调

唯一保证会执行到的钩子是注册的回调：

```cpp
const auto doShutdown = [&]()
{
    Utils::Out::outMsg("开始收尾：停止监听");
    // 1) 停两个监听 → io_context → join HTTP IO 线程
    // 2) 停连接维护线程
    // 3) 停主池 + 并行池
    // 4) 收微服务连接（stopConnectionMS）
    Utils::Out::outMsg("网关已退出");
};

Utils::Exit::registerStopCallback(shutdownGateway);   // 信号路径
Utils::Exit::waitExit();
shutdownGateway();                                     // 正常返回路径兜底
```

`call_once` 去重，因为**两条路径都可能调**：

```cpp
static std::once_flag once;
std::call_once(once, [&] { /* 收尾 */ });
```

## 回调里也不能让异常逃出去

这段代码跑在**信号处理线程**上，那里没有人接异常：

```cpp
std::call_once(once, [&]()
{
    try { doShutdown(); }
    catch (const std::exception &e) { Utils::Out::outErr(std::string("收尾异常：") + e.what()); }
    catch (...) { Utils::Out::outErr("收尾异常（未知）"); }
});
```

一个 `std::system_error`（比如 join 一个已 detach 的线程）就能让整个进程 `terminate`。

## 收尾顺序为什么是这样的

```
停监听 → join HTTP IO 线程   （不再有新请求进来）
  ↓
停连接维护线程                （它会调 callService / reconnectService）
  ↓
停两个线程池                  （在途请求的 worker 全部退出）
  ↓
收微服务连接                  （join 每条连接的 iot 线程）
  ↓
打"网关已退出"
```

顺序反了的后果：先停池子，在途请求的 worker 会拿着已经关掉的会话回包；先收连接，维护线程可能正在 join 一条已被清空的连接。

实测总耗时 **1064ms**（含 join 4096 线程的主池），远低于 Windows 给控制台处理器的 5 秒窗口。

# 连接维护：心跳 + 定时重连

## 为什么要单独一个线程

微服务会重启、会崩、会网络抖动。网关的"链路就绪"标志是**曾经连通**的痕迹，不代表现在可用。所以需要周期性地问一句"你还在吗"。

```cpp
inline int maintenanceIntervalMs = 60 * 60 * 1000;   // 1 小时
```

每轮做两件事：

```cpp
for (服务 : 配置表)
{
    if (!serviceLinkReady(no)) { reconnectService(no); continue; }   // 从没连上 / 上次判定断
    if (callService(no, 9000, "") != OK)      { reconnectService(no); }  // 心跳失败 → 当轮重连
}
```

心跳用内部健康检查命令号 `9000`：**走完整 RPC 链路**，能证明"服务真的在回包"，而不是"端口开着"。

## 原地重建：槽位下标不能变

连接容器是按下标对齐的（`MSClient[i]` / `runings[i]` / `toClient[服务号] = i`），所以重连必须**复用同一个下标**，不能 `push_back`：

```cpp
// 1) 锁内取快照（stop() 不能在锁内调）
// 2) 停旧连接 + 停 io_context
// 3) 把旧线程 move 出来（std::thread 不可拷贝），锁外 join
std::thread oldThread;
{ std::lock_guard lock(clientsMutex); oldThread = std::move(MSClient[index].iot); }
if (oldThread.joinable()) oldThread.join();

// 4) 先放掉旧 client，再换 io_context（铁律二）
// 5) 新 client + Connect() + 起线程（铁律一）
```

## 四段阶段日志

并发问题光读代码看不出来，所以重连里刻意打了四行：

```
重连：停止旧连接（服务 11）
重连：等待旧 IO 线程退出（服务 11）
重连：旧 IO 线程已退出（服务 11）
正在重连微服务：服务号 11 端口 9004（新连接已发出）
```

卡在哪一行，问题就在哪一段。我第一次就是卡在"等待旧 IO 线程退出"——根因是持锁调 `client->stop()` 造成的死锁。

## 实测时间线

```
11:09:44 对端已断开连接（×4）
11:09:45 等待服务号 11 回包超时（300ms）
11:09:45 维护：服务 11 心跳失败（状态 8），发起重连
```

## 启动策略：静默退出 vs 降级启动

```cpp
inline bool requireAllServicesReady = true;
```

- `true`（默认）：任一连不上 → **静默退出**（返回 1、只记日志、不弹框）
- `false`：降级启动，没连上的服务其路由返回 503，交给维护线程重连

"静默退出"是这次特意要求的：联调阶段没有微服务是常态，网关不该弹个 abort 框卡在那里。

# 排错手记

这一节全是"跑起来才发现"的东西，比 API 文档值钱。

## 桩服务的两个协议坑

自测网关时写了个 Python 桩服务（4 个端口，回合法空 `RpcResponse`）。第一版直接卡住，两次踩坑：

**坑一：回包 `length = 0`**

```python
# 错：空 payload
conn.sendall(struct.pack(">QI", msg_id, 0))
```

库判"消息长度错误"并直接断开。协议要求 1B ~ 1MiB，所以至少要回一个字节。最小的合法 `RpcResponse`：

```python
# {"head": {"msg_id": N}} → 0A 02 08 <varint N>
head = b"\x08" + varint(msg_id)
reply = b"\x0a" + varint(len(head)) + head
```

**坑二：回包 `Head.msg_id` 写死**

第一版桩把所有回包的 `msg_id` 都写成 1，结果 `/health` 显示 `11:ok, 20:21:22:down`——只有第一条对得上。

这反而**反证了网关的配对逻辑是对的**：`handleWork` 按 `head.msg_id` 找等待槽，找到 1 号槽就唤醒了它；其余三条的回包因为找不到槽，被当成"迟到回包"丢掉了。

## PowerShell 5.1 的三个坑

**坑一：没有 `-SkipHttpErrorCheck`**

```powershell
Invoke-WebRequest ... -SkipHttpErrorCheck   # 这个参数是 pwsh 7 才有的
```

5.1 里 4xx/5xx 会抛异常，`$_.Exception.Response` 也拿不到流。要看 4xx 的响应体只能裸 TCP：

```powershell
$c = [System.Net.Sockets.TcpClient]::new('127.0.0.1', 9001)
$s = $c.GetStream()
$req = "GET /api/v1/nope HTTP/1.1`r`nHost: g`r`nConnection: close`r`n`r`n"
$b = [Text.Encoding]::UTF8.GetBytes($req); $s.Write($b, 0, $b.Length); $s.Flush()
(New-Object System.IO.StreamReader($s)).ReadToEnd()
```

**坑二：无 BOM 的 `.ps1` 按 ANSI 解析**

用 `write` 写出来的脚本是 UTF-8 **无 BOM**，PS 5.1 会按系统代码页解析，中文全变乱码、语法直接报错：

```
Unexpected token '鐢ㄤ緥' in expression or statement
```

两个办法：脚本里**不写非 ASCII 字符**，或者落盘时加 BOM。

**坑三：`SetConsoleCtrlHandler(NULL, TRUE)` 会被子进程继承**

想给网关发 Ctrl+C 验证优雅退出，第一步先让测试脚本自己忽略 Ctrl+C：

```powershell
[CtrlApi]::SetConsoleCtrlHandler([IntPtr]::Zero, $true)
```

结果广播出去的 Ctrl+C **网关也收不到**——这个"忽略"标志是**创建子进程时继承**的，而网关是在设置之后启动的。

正确的验证方式有两种：

- 先启动子进程、再设置自己忽略（顺序反了就没用）；
- 更省事：`Start-Process` 让网关**独立开一个控制台窗口**，再用 `taskkill /PID <pid>`（**不带 `/F`**）关窗口。这会触发 `CTRL_CLOSE_EVENT`，等价于用户点窗口的 ×，且不影响测试进程。

## 只读状态行验证 204

`httpAsyncReplay` 对空 body 的处理是"忽略"，所以真正的 204 会让客户端**一直等不到响应**（不是 500，是挂住）。验证时不能在 204 上用 `ReadToEnd()`（等不到 EOF 会挂），只读第一行：

```powershell
$sr = New-Object System.IO.StreamReader($s)
"状态行: $($sr.ReadLine())"
```

## 用日志定位"卡在哪"

并发 bug 首选手段不是打断点，而是**阶段日志**。重连那四行、收尾那六行，都是为了让"卡住"能定位到具体一步：

```
收尾：IO 线程已结束
收尾：连接维护线程已停止
收尾：线程池已停止
收尾：微服务连接已关闭
网关已退出
```

少哪一行，问题就在那一段。

# 库层面的已知限制

写成清单，避免以后重复踩：

| 限制 | 影响 | 临时对策 |
| --- | --- | --- |
| `httpAsyncReplay(seq, body, st)` 的**空 body 会被忽略** | 所有 `Empty` 响应（标准 204）客户端收不到，挂到超时 | 默认回 `200 + {}`，留 `emptyResponseAsNoContent` 开关 |
| 没有"带响应头"的重载 | `Set-Cookie` 设不了，refresh 令牌只能放响应体 | 留 `GATEWAY_REPLY_HAS_HEADERS` 宏 |
| `Url` 里**没有客户端地址** | 按 IP 限流/统计做不了 | 限流 key 先用账号/会话 |
| 没有 Redis 客户端 | 幂等去重做不了 24h，只能透传 | 服务侧兜底 |
| 队列满会丢任务（已修） | 请求永远不回包 | 抛异常 + 积压阈值 + 带超时等待 |

# 测试驱动：那些只有跑起来才暴露的问题

自动化测试跑完给了一张 117 项的清单（✅70 / ⚠️17 / ❌8 / ℹ️22）。逐条修的过程里，有一半"失败"其实是**测试自己在说谎**——不是断言写错，而是测试构造的请求和真实前端根本不是一回事。

## 慢 ≠ 死：超时不能判链路已死

最典型的一次。超时用例（上游故意延迟 700ms、网关 300ms 超时）拿到了 **503**，而期望是 504。

503 在我这套代码里只有一个来源：`pickClient` 的"链路未建连"——也就是链路标志被置成了 `false`。追下去，是我自己上一版写的"连续 2 次等不到回包就判定链路已死并立刻重连"：

```cpp
// 错的：把"慢"当成"死"
if (streak >= 2)
{
    runings[index]->store(false);      // 链路标志置断
    reconnectService(serviceNo);       // 立刻重连
}
```

压测里上游只是**慢**，第一次超时后它其实还在回包；连着两次超时就把整条链路拆了，后续请求全部 503，`/ready` 也跟着抖。

改成"超时只触发一次健康复核，判死交给心跳"：

```cpp
if (streak >= kFailuresBeforeHealthCheck)   // 2 次
{
    // 只叫醒维护线程发一次 9000 心跳，**不判死**
    Maintenance::kick();
}
```

维护线程跑一轮心跳：通了什么都不做（只是慢），不通才 `reconnectService`——而重连那一步才会把链路标志置 `false`。

**结论**：多个信号要分层。"请求超时"是**弱信号**（可能是慢、可能是网络抖动），"心跳也不回"才是**强信号**。用弱信号做破坏性动作（拆链路、置断、重连），迟早误伤。

## 502 的 body.status 必须等于响应行

```json
HTTP/1.1 502 Bad Gateway
{"status": 500, ...}     ← 前端按 body.status 判断，看到的是"网关内部错误"
```

`makeErrorReply` 内部用 `RpcStatus → HTTP` 的映射表反推状态，而"上游给了 200 但报文不是约定类型"这个失败在 `RpcStatus` 里没有对应值，只能传 `INTERNAL`，于是 body 写成 500。

修法是给错误出口加一个**显式 HTTP 状态**的重载，两者共用同一个拼装函数：

```cpp
std::string makeErrorReply(RpcStatus status, ...);                    // 常规：映射
std::string makeErrorReply(http::status http, RpcStatus status, ...); // 语义不重合：显式给
```

同样的坑还藏在"过载 503"：`RESOURCE_EXHAUSTED` 会映射成 429，HTTP 却是 503。

**结论**：只要项目里存在"由 RpcStatus 推 HTTP 状态"的映射，就必然存在映射不到的情况。错误体里的 `status` 必须和响应行同源，不能各自算。

## 前缀匹配：少一个 s 就是另一条链路

前缀表里写的是 `/api/v1/admin/notification`，而真实接口是 `/api/v1/admin/notifications/resend`。

前缀匹配按**整段边界**比对，第 14 个字符是 `s` 而不是 `/`，所以单数前缀匹配不上复数路径，请求落到了更短的 `/api/v1/admin` → user-svc，而不是 notice-svc。

文档写的是 `/api/v1/admin/notification*`（星号表示"通知管理整段"），实现时按字面抄成了单数。

**结论**：文档里的通配写法不能直译成代码里的前缀。要么统一成实际路径的复数形式，要么在边界规则上显式支持"前缀词"(prefix-word) 语义——两者选一，别含糊。

## 同一路径、不同方法 = 不同请求类型

方法矩阵跑 103 条路由 × 8 种方法，出现了 32 个 400。

原因：

```
GET  /api/v1/competitions → 3001  GetCompetitionListRequest { page, keyword, sort, ... }
POST /api/v1/competitions → 3004  CreateCompetitionRequest   { draft { ... } }
```

测试用 3001 的模板跑 `POST`，期望命中 **3004**，但请求体是按 **3001 的请求类型**生成的——网关按 `CreateCompetitionRequest` 解析，遇到 `page`/`keyword` 就是未知字段，直接 400。

修法是让请求体跟着"实际命中的命令号"走：

```python
expected_cmd, _ = expected_command(method, path)
body = route_body(expected_cmd, method) if expected_cmd else None
```

**结论**：路由的"路径"不是请求体的唯一决定因素，`(method, path)` 才决定命令号，命令号才决定消息类型。任何"按模板造请求"的工具都要走完整匹配，不能只按路径。

## 时钟容忍窗口：测试取值要远离边界

JWT 的 `exp`/`nbf` 允许 ±60s 时钟偏移。测试里写的是：

```python
("exp 已过期 31s", ...)   # 期望 401
```

31 秒落在 60 秒容忍窗口内 → 网关正确放行 200 → 测试判失败。这是**测试按旧口径（30s）写的**，实现后来按文档改成了 60s。

改的时候还有个坑：不能直接改成 59/61。

- 59s：令牌批量构造、逐条请求要跑几秒，可能刚好滑出窗口；
- 61s 的 nbf：跑几秒后可能滑进窗口。

最后取 **30s（窗口内）/ 120s（窗口外）**，离边界足够远。

**结论**：凡是"边界值"用例，取值必须离边界有**大于测试自身耗时的余量**，否则就是随机失败的定时炸弹。

## 断言共用 trace 会让用例自我欺骗

路径变体测试给同一条路由造了 12 种路径（尾斜杠、重复斜杠、多一段、少一段……），但 12 个变体**共用同一个 `X-Request-Id`**：

```python
trace = trace_id(f"pv-{command}")     # 12 个变体都一样
...
fx.check(..., bool(fx.find(trace, expected_cmd)))   # 会捞到前面变体的记录
```

`find(trace, ...)` 是"按 trace 查上游收到的请求"，共用 trace 意味着**前一个变体的记录会让后一个变体的断言蒙对**（也可能蒙错）。断言看起来绿，其实没验证任何东西。

改成每个变体独立 trace：

```python
trace = trace_id(f"pv-{command}-{name}")
```

**结论**：用"关联 ID"做断言时，ID 的粒度必须和断言的粒度一致。一个 ID 覆盖多个用例，等于放弃断言。

## 测试桩：单条请求异常不能关连接

有一轮测试出现了 7593 个失败，看网关日志：

```
服务号 11 的链路标记为断开：等待回包超时（连续 2 次）
重连：停止旧连接（服务 11） → 旧 IO 线程已退出 → 新连接已发出
对端已断开连接        ← 刚连上又被断开
```

根因在**桩**这一侧：Python 桩的请求分发函数抛了异常（`AttributeError`），而它的读循环是

```python
try:
    ...dispatch...
finally:
    conn.close()      # 任何异常都关连接
```

一条请求处理失败 → 关连接 → 网关判定链路死 → 重连 → 桩又抛 → 再关……形成**重连风暴**，后面成片的用例全部 503。

改法是把"单条请求失败"和"连接失败"分开：

```python
try:
    dispatch(...)
except Exception as exc:
    # 回一条错误信封，**不关连接**
    send(msg_id, encode_response(msg_id, 13, "STUB_ERROR", str(exc)))
```

**结论**：测试桩的健壮性直接决定测试结果的可信度。桩的一条异常如果升级成"连接断开"，会被被测系统的容错逻辑放大成系统性故障——这时你看到的红，测的是桩，不是网关。

## 测试工具自身的状态也要管

JWT 测试工具每次运行都**重新生成 RSA 密钥对**并覆盖公钥文件，而网关只在启动时加载公钥。于是下一批令牌全部验签失败 → 所有需要登录的用例 401，现象看起来像"验签逻辑坏了"。

修法是密钥**持久化**（存在就复用），并把"生成密钥"和"签令牌"拆成两步。

同类问题还有：令牌生成后隔了几十秒才发请求（`exp` 早已过期）、用 `kill` 进程名杀桩时把测试脚本自己也杀了（都是 python）。

**结论**：测试基础设施也是代码，也需要"状态管理"。凡是跨运行保留的东西（密钥、文件、端口、进程），要么显式清理，要么显式复用——不能靠"每次都是新的"这种假设。

# Redis：网关真正需要它的四个地方

网关不碰业务数据：没有 MySQL 连接、不发 MQ 事件、不直传文件。但有一类状态它必须自己持有——**"这个请求是不是重放""这条令牌是不是已登出""这个人的权限集是什么"**。这三件事都属于"跨请求、跨实例、会过期"的状态，正好是 Redis 的活。

## 一、客户端层：连接池 + 超时 + 可选依赖

hiredis 的 `redisContext` **不是线程安全的**：同一个 context 上并发 `redisCommand` 会串包。而网关有 4096 个 worker，所以必须池化——一条命令独占一条连接，用完归还。

```cpp
// 借还的 RAII 包装：任何提前 return 都能安全归还，不漏还
class Guard
{
public:
    Guard() : ctx_(acquire()) {}
    ~Guard() { release(ctx_, healthy_); }
    redisContext *get() const { return ctx_; }
    void ok() { healthy_ = true; }
};
```

三条硬要求：

1. **必须有超时**：`redisConnectWithTimeout` + `redisSetTimeout`，300ms，和 RPC 超时一致。Redis 卡住不能把 4096 个 worker 一起拖死。
2. **编译期可选**：`find_path`/`find_library` 探测 hiredis，没有就编译空实现。

```cmake
find_path(GATEWAY_HIREDIS_INCLUDE_DIR hiredis/hiredis.h)
find_library(GATEWAY_HIREDIS_LIBRARY NAMES hiredis)
# 有 → GATEWAY_HAS_HIREDIS=1；没有 → =0，Redis.cpp 走空实现分支
```

3. **运行期 fail-soft**：连不上只打一条告警，网关继续启动。

```
Redis 不可用（127.0.0.1:6379），幂等/jti/权限缓存降级：
幂等仅透传、jti 不校验、权限集用进程内缓存
```

**为什么"可选"很重要**：如果 Redis 是硬依赖，那任何一次"机器上没起 Redis"都会变成"网关编译不过"或"网关起不来"。把降级路径**编译进**代码里，才能保证"少一个基础设施，能力减弱但服务还在"。

## 二、幂等去重：只缓存成功，且记忆点在最后

`Idempotency-Key` 是前端防重复提交的约定。网关侧要做的是"同一 key 在 24h 内重放时，直接把首次的结果回放给他，不再打上游"。

```cpp
std::string cacheKey(key, accountId)        // tzb:gw:idem:{account_id}:{key}
```

四个刻意的决定：

**① 只缓存 2xx**

```cpp
if (status < 200 || status >= 300) return;   // 4xx/5xx 不缓存
```

4xx/5xx 可能是瞬时的（上游抖动、限流）。缓存下来会把**一次偶发失败变成 24 小时的确定性失败**。

**② 记忆点放在 BFF 补字段之后**

网关会给队伍详情补成员姓名（BFF 兜底），补失败时返回体带 `degraded:true`。如果在上游回包时就缓存，重放拿到的 body 和首次客户端看到的**不一致**——少了补好的姓名。所以：

```cpp
// 先做 BFF enrich、空响应兜底，最后才 remember
if (!idemKey.empty() && authenticated && supported(command))
    remember(idemKey, actor.account_id(), 200, url.body);
```

**③ 键里带 account_id**：不同账号用了同一个 uuid（前端写死）互不影响。

**④ 未登录不做**：幂等键挂在账号下，匿名请求没法安全区分。

存储格式用 `"<status>\n<body>"`：

```
200
{"id":"1843920517801234432","name":"..."}
```

网关输出的 JSON 是紧凑格式、不含换行，所以第一个 `\n` 之前一定是状态码。比再套一层 JSON 省事，也不会因为转义把响应体放大。数据损坏时**删键并按未命中处理**——宁可多转发一次，也不能把坏数据回给前端。

## 三、jti 黑名单：TTL 等于剩余寿命

access 是自包含的 JWT：验签通过就代表"签发时是真的"。但**撤销**需要外部状态——签名没法撤回。

做法是把 `jti` 记进 Redis，**TTL 取令牌的剩余有效期**：

```cpp
Gateway::Blacklist::revoke(jti, exp - now);
```

这个 TTL 的选择是有意的：令牌自然过期后，黑名单记录自动消失，**名单不会无限增长**。如果统一给 24 小时，那 30 分钟有效期的令牌会白占 23.5 小时的键空间。

两个边界：

- **改密不逐条拉黑**：A-08/A-09 由服务侧递增 `perm_ver` 让旧令牌整体失效，不需要遍历所有会话的 jti。
- **Redis 挂了整体放行**：只打一条告警。取舍很明确——宁可让已登出的令牌多活几分钟，也不能因为 Redis 挂了让全站登录不可用。

`claimOf` 这个小函数也值得说一句：

```cpp
/// @warning **不验签**！只应在 verifyJwt 成功之后调用。
bool claimOf(token, jti, exp, error);
```

它只解码 payload 取 `jti`/`exp`。给它任意伪造的令牌都会"解析成功"，安全边界完全依赖调用方先验签——所以这条警告必须写在头文件里，而不是实现里。

## 四、权限集缓存：两级 + perm_ver 进键名

改造前是纯进程内缓存。改成两级后：

| 层 | 键 | TTL | 作用 |
| --- | --- | --- | --- |
| L1 | 进程内 map | 5 分钟 | 常规命中，零网络往返 |
| L2 | `tzb:gw:perm:{account_id}:{perm_ver}` | 5 分钟 | 多实例共享，避免每台各自回源 A-05 |
| L2 | `tzb:gw:acc:{account_id}` | **60 秒** | 账号状态独立，停用/锁定要及时生效 |

命中顺序 L1 → L2（两个键都在才算命中，命中后回填 L1）→ 回源 A-05（写回两层）。

**为什么 `perm_ver` 要进键名**：

```cpp
"tzb:gw:perm:" + account_id + ":" + perm_ver
```

角色一变、`perm_ver` 一变，旧键自然读不到。**不需要服务侧配合"删缓存"**——那种设计最容易漏：改角色的人忘了删，前端就拿着旧权限继续用，而且这种 bug 只在"刚改完权限"的几分钟里出现，最难复现。

**为什么状态不跟权限一起缓存 5 分钟**：权限可以脏 5 分钟，账号状态不行。一个人被停用了，最多 60 秒就该被拦住。

## 排错手记：三个只有真跑起来才会遇到的坑

**① 没装 hiredis 时，测试不能"假绿"**

M5（幂等）和 M9（jti 黑名单）依赖 Redis。如果测试硬断言"必须有去重/必须 401"，那没编译 hiredis 的机器上就是一片红；反过来如果断言"没有去重"，编译了 hiredis 又是一片红。

做法是让用例**先探测能力，再决定断言**：

```python
forwarded = fx.stub_count(21, 4001) - before
if forwarded == 1:          # 去重生效
    断言：重放未转发上游 / 状态码一致 / 响应体一致 / 换 key 会重新转发
else:                       # 降级
    fx.known("幂等去重未启用（未编译 hiredis 或 Redis 不可用）")
```

**② 测试账号 ID 会跨轮"串缓存"**

网关的权限/状态缓存在 Redis 里，键是 account_id。而测试的账号 ID 每次运行都从同一起点递增——上一轮把某个号标成 `DISABLED`，这一轮新建的同号账号还没回过源就被 403 拦下。

修法是给每轮一个随机起点：

```python
_ACCOUNT_BASE = 900000000000000000 + (uuid.uuid4().int % 10**12) * 1000
```

**③ WSL2 里的 Redis，Windows 上能不能连**

`redis-cli ping` 在 WSL 里是 `PONG`，但那是 WSL 自己的 localhost。Windows 侧要单独验：

```powershell
Test-NetConnection -ComputerName 127.0.0.1 -Port 6379
```

`TcpTestSucceeded : True` 才能用默认配置（WSL2 有 localhost 转发）。不通的话要么改 `bind 0.0.0.0` + 关 `protected-mode`（仅本地演示），要么用 `wsl hostname -I` 拿到的 IP 配 `TZB_GW_REDIS_HOST`。

# 响应头与 204：库补上一块能力之后

前面几轮一直有几项实现不了，原因都指向同一个地方：**`httpAsyncReplay` 只有 `(seq, body, st)`**。于是 `Set-Cookie` 写不出去、`X-Request-Id` 回不了、204 也不敢回（空 body 会被库丢弃，客户端一直挂到超时）。

库更新后这两块终于补上了：

```cpp
using ResponseHeaders = std::vector<std::pair<std::string, std::string>>;

void httpAsyncReplay(unsigned long long seq, const std::string &body,
                     boost::beast::http::status st, const ResponseHeaders &headers);

// 空串会原样发送，得到 Content-Length: 0 的响应
```

## 四项一次收口

| 项 | 改法 |
| --- | --- |
| `Set-Cookie` | 登录/刷新成功后把 refresh 从响应体摘掉，写 `Set-Cookie: tzb_rt=…; HttpOnly; SameSite=Strict` |
| 标准 204 | Empty 响应回 `204` + 空 body |
| `X-Request-Id` | 客户端带了就回写，没带不回 |
| `X-Cache` | 统一 `BYPASS` |
| `application/problem+json` | 4xx/5xx 追加 `Content-Type`，**覆盖**库默认的 `application/json` |

两个细节值得说：

**① `X-Cache` 回 `BYPASS` 而不是编一个**

网关**没有读缓存层**。规范允许 `HIT|MISS|BYPASS`，`BYPASS` 的语义正是"这次绕过了缓存直达上游"——它诚实地描述了现状。硬凑一个 `MISS` 反而会让人以为"缓存存在但没命中"，那是另一种谎。

**② `X-Request-Id` 没带就不回**

凭空生成一个 id 回给前端，只会让人以为"是我发的那条"，排查时对着一个不存在的 trace 找半天。没有就空着，语义明确。

## thread_local 从"一个 Cookie"升级成"一组头"

原来是 `thread_local std::string replyCookie`，只够放 Set-Cookie。现在要放多个头：

```cpp
std::vector<std::pair<std::string, std::string>> &replyHeaders()
{
    thread_local std::vector<std::pair<std::string, std::string>> headers;
    return headers;
}
```

安全性没变：一个请求从"路由设头"到"Handler 回包"全程在同一个 worker 线程、同一个任务内，不跨线程也不会被并发请求串味。`setReplyHeader` 对同名头是**覆盖**而不是追加——网关只会设置一次 `X-Request-Id`/`X-Cache`，真出现两次说明业务写错了。

## 参数顺序踩过一次

新重载是 `(seq, body, st, headers)`，**headers 在最后**。而之前为了"库以后会加响应头"，代码里按草案写成了：

```cpp
session->httpAsyncReplay(req.seq, headers, req.body, st);   // 编译不过
```

类型不同（`vector` vs `string`）所以编译期就报错，没进运行时。这种"提前为未来写好"的代码最危险的地方不是写错，而是**如果两个参数恰好同类型**就会静默错位。所以参数顺序要在头文件注释里写死。

## 一个开关只能有一处

"空响应回 204 还是 200+{}"这个决定，代码里有两处要用：文件末尾的统一出口，和 telemetry 成功路径。两处都读同一个 `Config::emptyResponseAsNoContent`——**如果各写一套，行为迟早漂移**（改了一处忘了另一处，前端会在某个接口上莫名收到 200+{}）。

## 测试侧：Empty 命令的成功状态变了

真正麻烦的不是 C++，是测试。`tzb.common.v1.Empty` 响应的命令有 18 条（登出、发码、删除、标记已读……），它们在 A1/A5/A6/C1/C2/E7/M2/M7/M9 里全都被断言成"200 + `{}`"。

所以先在模型里把口径统一：

```python
def ok_status(command: int) -> int:   # Empty → 204，其余 → 200
def ok_body(command: int) -> str:     # Empty → ""，其余 → "{}"
```

所有"路由遍历 / ACL / 公开接口"的断言都改用它。

## 然后踩了一个自己挖的坑：用期望值当分类键

改完第一轮跑，**84 个失败**，全在 A5（方法矩阵）和 A6（路径变体），失败名却是：

```
POST /api/v1/auth/logout 缺 Cookie 不转发
1004 短 query 缺 Cookie 不转发
```

1004 是登出、1007 是发码，跟 refresh Cookie 毫无关系。看原来的分支：

```python
if want_status == 200:      # 命中 → 校验命令号
    ...
else:                       # 当时只可能是 1003 的 401 → 校验"没转发"
    fx.check(..., "缺 Cookie 不转发", not fx.find(trace), ...)
```

`want_status` 从 200 变成 204 之后，`== 200` 不成立，于是**所有 Empty 命令都掉进了"缺 Cookie"分支**，去断言"这条请求不该被转发"——而它们本来就该转发。

根子在于：**`want_status` 是数据（期望的状态码），不是分类（这条用例属于哪一类）**。用数据当分类键，数据的取值范围一变（200 → 204），分类就错。

正确的分类键必须稳定：

```python
# 分支看**是不是 1003**，不能看 "want_status == 200"
if expected_cmd == 1003:
    fx.check(..., "缺 Cookie 不转发", not fx.find(trace), ...)
else:
    fx.check(..., "命中命令号", bool(fx.find(trace, expected_cmd)), ...)
```

这类 bug 有个共同特征：**它只在"期望值集合扩大的那一刻"出现**，而且报错信息还指向完全无关的功能（Cookie）。看到"某个用例的失败名和它测的东西对不上"时，先怀疑断言结构，而不是被测代码。

# Turnstile：网关的第一次出站 HTTPS

网关一直只做"进站"：收 HTTP、验 JWT、转发 RPC。人机验证（Turnstile）是第一个**必须自己发出 HTTPS 请求**的需求——前端拿到的 token 不可信，必须由服务端调 Cloudflare 的 `siteverify` 确认。

## 为什么不能只透传

最早的做法是把 `captcha_token` 原样转发给 user-svc，让服务侧校验。问题是：

- **服务侧没有出网**（也不该有）：微服务跑在内网，只连 dbpool 和 MQ；
- **网关是唯一该出网的组件**：它本来就要面对公网流量，多一条出站调用不改变它的信任边界。

所以这件事只能落在网关上。

## 四个"放在哪儿"的决定

**① 校验点放在 JSON→proto 之后**

顺序很重要：坏 JSON、未知字段要先按 `400 INVALID_ARGUMENT` 回掉。如果把验证码放在最前面，一个 JSON 语法错误会被报成 `CAPTCHA_REQUIRED`，前端就去刷新验证码了——**报错指错方向，比报错更贵**。

**② 登录只在校验带 token 时做**

文档要求"登录第 3 次失败起强制人机验证"。但"第几次失败"是**服务侧的状态**（`account.failed_count`），网关不知道，也不该去查。

所以网关只做它知道的事：请求里带了 token 就校验；没带就放行，让服务侧回 `captcha_required: true`，前端补上 token 再来一次。

**③ 网络错误重试一次，`success=false` 不重试**

```cpp
if (!ok) {                       // 只有网络/5xx 才重试
    ok = postSiteverify(form, responseBody);
}
```

`success=false` 是"用户真的没过"，重试一百次也是不过，只是白花两次 CF 配额。而网络抖动重试一次，能把"偶发超时"和"真挂了"区分开。

**④ 不确定时按"拒绝"处理**

```cpp
if (!ok) {
    noteFailure(remoteIp);
    return reject(503, "CAPTCHA_UNAVAILABLE", "人机验证服务暂时不可用，请稍后重试");
}
```

CF 挂了、网络不通、响应不是 JSON——这几种都属于"我不知道这个 token 是不是真的"。文档 §1.2.6 给了分级策略（低风险放行、高风险拒绝），网关取了"拒绝"这一档：注册、发码、登录都是可重试的操作，让用户点一次重试，比放行一个人机请求便宜。

## 两个防滥用的缓存

**PASS 缓存**：`tzb:gw:tsv:{sha256(token)}=PASS`，TTL 300s（与 token 同寿命）。

- 键里放 **sha256** 而不是原始 token：Redis 的键会被 `KEYS`/`SCAN` 看到，token 不该以明文躺在那里；
- 副作用正好是防重放：同一个 token 第二次直接放行，不再打 CF。

**失败计数**：`tzb:gw:rl:captcha:{ip}`，10 次 / 10 分钟。

超过就不再打 CF——否则别人可以拿我们的网关当"打 Cloudflare 的跳板"，花的是我们的配额。

## 测试：先造一个"假 Cloudflare"

网关现在要出网，测试环境却没有网。所以桩也得升级：`gw_stub` 原来只讲 12 字节头的 RPC 协议，这次加了一个**真的 HTTP 服务**（9020 端口），按 token 前缀给出可预测的判决：

| token 前缀 | 桩返回 | 网关应回 |
| --- | --- | --- |
| `bad-*` | `success=false` + `invalid-input-response` | 403 `CAPTCHA_INVALID` |
| `expired-*` | `success=false` + `timeout-or-duplicate` | 403 `CAPTCHA_EXPIRED` |
| `wrong-action-*` | `success=true` + `action=login` | 403 `CAPTCHA_INVALID`（跑 `send_code` 场景） |
| `unavailable-*` | HTTP 500 | 503 `CAPTCHA_UNAVAILABLE` |
| 其它 | `success=true` | 放行 |

网关启动时用环境变量把 `TZB_GW_TURNSTILE_URL` 指到 `http://127.0.0.1:9020/...`——所以这个模块**同时支持 http 与 https**，不是为了生产，是为了测试。

写这个桩的时候踩了一个小坑：它必须按 `Content-Length` 读完 body 再回包。第一次只读了 `\r\n\r\n` 就回，结果拿到的是空的 `response`，判决全错。

## K6/K7：拒绝的姿势也要讲究

顺带把两个"库限制"收了。

服务端对超限请求（>32MB body / >8KB header）必须拒绝。但拒绝的**姿势**决定客户端能不能看到状态码：如果接收缓冲里还有未读字节就直接 `close()`，内核会发 RST，把刚写出去的 413/431 一起废掉，客户端只看到"连接被重置"。

新库的做法是 `drainAfterReply`：先写响应、把对端残余数据读掉（有上限，防无限灌）、半关闭发送方向、再关连接。

所以：

- **网关这一侧什么都改不了**——拒绝发生在业务回调之前，网关只决定额度（`maxHttpBodyLen` / `maxHttpHeaderLen`）；
- 测试从"接受断连"改成断言 **431**；K6 仍接受"413 或断连"，因为排空有上限，33MB 的客户端很可能在**写**阶段就收到 EPIPE——那不是服务端没回，是客户端还没写完。

# 经验

- **顺序是独立的一类 bug**。`Connect()` 与 `run()` 的先后、`client` 与 `io_context` 的销毁先后、收尾里"停监听→停池→停连接"的先后——每一处顺序错了都不报错，只是**不工作**或**卡死**。
- **静默失败最贵**。空 body 被丢、`atomic` 未初始化、`outFileAdd` 写成功也返回 false、future 永远不会 ready……这些都不是崩溃，是"看起来没反应"。凡是"没反应"的地方，第一件事是找**有没有一条日志能证明它执行过**。
- **同步 API 包异步框架，一定要有超时**。`waitFanout`、`callService`、心跳，全都带超时。没有超时的等待，在故障时就是永久挂起。
- **并发 bug 靠日志定位，不靠读代码**。四段阶段日志花五分钟，省一下午。
- **库的"方便"往往带隐性契约**。"空串会被忽略"六个字，让所有 204 响应静默失效；"队列满丢弃任务"两行代码，能让请求永远不回包。用别人的库，`@warning` 和 `@note` 要逐条读。

# 补丁批次：把「卡在库层」的 7 项做进 Net

网关那边验收完，还剩 7 项**全部卡在 Net 库**而不是网关逻辑：两个超限响应的边界行为（K6/K7）、三个响应头（M1/M3/M4）、空 body 语义（M2）、出站 HTTP（M8）。这一批按「一个功能一个提交」做，下面只记真正学到手的知识点。

先给结论性的对应关系：

| 需求 | 提交 | 本质 |
| --- | --- | --- |
| M1/M3/M4 响应头 | `feat(http): 支持自定义响应头` | 回包接口缺一个「附加头」参数 |
| M2 空 body | `feat(http): 空 body 也能照常回包` | 一个历史约定把合法响应当成了控制信号 |
| K6 413 后被 RST | `fix(http): 请求体超限稳定回 413` | 拒绝时机判断错 + close 前没排空 |
| K7 请求头超限 | `fix(http): 请求头超限回 431` | 同上，只是错误码不同 |
| M8 出站 HTTP | `feat(http): 新增出站 HTTP 客户端` | 库里只有 server，没有 client |

## 一、先搞清楚：改的是"库"还是"端"

这一批之前的纠结，全在 vcpkg 上：自研库要不要做成端口、装的是不是最新、为什么改了代码包没变。踩完之后的结论很朴素：

- **vcpkg 装的是编译好的快照**，不是指向源码的链接。改 `.cpp`、改头文件（哪怕只改注释），`installed\` 里那份都不会动。
- **`vcpkg install` 会骗你**。它判断要不要重建只看「版本号 + portfile 哈希 + 依赖 ABI」，**不看源码树**，所以源码改了它照样打印 `already installed`，2.73 ms "成功"。
- **必须 `remove` + `--no-binarycaching`**。少了第二个参数，vcpkg 会从 `%LOCALAPPDATA%\vcpkg\archives` 把**上一次**的构建解压回来——因为 ABI 没变，缓存里存的就是旧包，你还以为装上了。

```powershell
.\vcpkg.exe remove    commonnet:x64-windows
.\vcpkg.exe install   commonnet:x64-windows `
    --overlay-ports=<Net仓库>\ports `
    --overlay-ports=<Utils仓库>\ports `
    --no-binarycaching
```

判断「装的是不是当前源码」，别信 `vcpkg list`（它只读台账），直接比哈希：

```powershell
(Get-FileHash <仓库>\HttpServer\include\NetHttpServer.h).Hash -eq
(Get-FileHash D:\vcpkg\installed\x64-windows\include\Common\Net\HttpServer\NetHttpServer.h).Hash
```

台账和文件可能对不上——这一轮就遇到过 Boost 的台账说"已装"、实际文件被卸空的情况。**台账 + 文件 + 时间戳**三样一起看才作数。

## 二、端口化：三个半文件，一个 trick

`ports/commonnet/` 就四样东西：

```
vcpkg.json       # 端口清单：包名、版本、依赖（utils / openssl / 两个 host 工具）
portfile.cmake   # 构建说明：源码从哪来、怎么配、怎么装、怎么修配置
usage            # 装完 vcpkg 打印的使用说明
LICENSE          # 随包安装的 copyright
```

最有用的技巧是**本地源码优先**——端口放在源码仓库里时，直接拿工作区当源码，免 push、免联网、免改 SHA512：

```cmake
get_filename_component(_commonnet_port_parent "${CMAKE_CURRENT_LIST_DIR}/../.." ABSOLUTE)
if(EXISTS "${_commonnet_port_parent}/CMakeLists.txt")
    message(STATUS "commonnet: 使用本地源码树 ${_commonnet_port_parent}")
    set(SOURCE_PATH "${_commonnet_port_parent}")
else()
    vcpkg_from_github(... REF "v${VERSION}" SHA512 ...)  # 正式发布时才走这条
endif()
```

代价是**每次改源码都要重装**，所以它的定位是"发布物"，不是开发入口。日常迭代还是 `cmake --build build`，只在要给下游交付时才刷包。

## 三、`VCPKG_LIBRARY_LINKAGE` 会覆盖你传的 `BUILD_SHARED_LIBS`

这是这一批最阴的一个坑。

Net 的公开头文件**没有任何 `__declspec(dllexport)`**，所以只能编静态库：动态化会得到"导出表为空"的 DLL，连导入库都生成不出来，下游一链接就是 `LNK1104: 无法打开文件 CommonNetCore.lib`。

于是我在端口里传了 `-DBUILD_SHARED_LIBS=OFF`——**没用**。因为 `vcpkg_cmake_configure` 内部会按三元组再追加一次：

```cmake
# installed/<triplet>/share/vcpkg-cmake/vcpkg_cmake_configure.cmake
if(VCPKG_LIBRARY_LINKAGE STREQUAL "dynamic")
    vcpkg_list(APPEND arg_OPTIONS "-DBUILD_SHARED_LIBS=ON")
elseif(VCPKG_LIBRARY_LINKAGE STREQUAL "static")
    vcpkg_list(APPEND arg_OPTIONS "-DBUILD_SHARED_LIBS=OFF")
endif()
```

而且**追加在端口 `OPTIONS` 之后**——同一个 `-D` 后写的赢，所以我们的 `OFF` 被覆盖成 `ON`。正解是在端口里直接改链接方式：

```cmake
set(VCPKG_LIBRARY_LINKAGE static)   # helper 于是自己追加 -DBUILD_SHARED_LIBS=OFF
```

教训：**遇到"我明明传了参数却没生效"，先去看 helper 的源码**。`vcpkg_cmake_configure.cmake` 就几百行，比猜快得多。

## 四、`config_fixup` 改的是"相对层数"

`install(EXPORT)` 把配置装到 `lib/cmake/CommonNet`（三层深），`vcpkg_cmake_config_fixup(CONFIG_PATH lib/cmake/CommonNet)` 会把它挪到 `share/commonnet`（两层深），并**重写前缀计算**：

```cmake
# 修之前（lib/cmake/CommonNet 上三级 = prefix）
get_filename_component(PACKAGE_PREFIX_DIR "${CMAKE_CURRENT_LIST_DIR}/../../../" ABSOLUTE)
# 修之后（share/commonnet 上两级 = prefix）
get_filename_component(PACKAGE_PREFIX_DIR "${CMAKE_CURRENT_LIST_DIR}/../../" ABSOLUTE)
```

验证方式很直接：装完打开 `share/commonnet/CommonNetConfig.cmake`，看是两级还是三级。如果没被改写，`find_package` 能找到包，但库路径会整体错位一级——**这种错最贵，因为配置期不报错**。

## 五、`/utf-8` 必须 PUBLIC，否则中文注释会吃掉换行

这个 bug 的现场极有迷惑性：下游 `#include "NetServer.h"` 编译，报

```
NetServer.h(49): error C2530: "msg_id": 必须初始化引用
```

而实际代码里 `using HandleFunction = ...` 在**第 56 行**——差 7 行。

原因是三件事叠在一起：

1. 头文件是 **UTF-8 无 BOM**；
2. 换行是**纯 LF**（不是 CRLF）；
3. 消费端编译时没有 `/utf-8`，MSVC 按系统 ANSI（GBK）解析。

于是在 GBK 视角下，某行中文注释的**最后一个字节**会和后面的换行组合成一个"合法"的多字节字符，把下一行代码并进注释。一个注释吃一行，7 个注释就吃掉 7 行——编译器看到的就是"第 49 行".

> 为什么 CRLF 能躲过？因为即使最后一个字节吞掉 `\r`，`\n` 还在，换行仍然成立。**纯 LF 才是致命的那个条件。**

修法是把 `/utf-8` 从 `PRIVATE` 改成 `PUBLIC`（用生成器表达式限定 MSVC，别塞给 GCC/Clang）：

```cmake
target_compile_options(${target} PRIVATE /MP /FS)
target_compile_options(${target} PUBLIC $<$<CXX_COMPILER_ID:MSVC>:/utf-8>)
```

因为库自己的 `.cpp` 一直带着 `/utf-8`，所以**库编得过、下游编不过**——这类"一半好一半坏"的 bug，最容易误判成"下游用错了"。

## 六、`Content-Length` 超限，是在"解析请求头"阶段被拒的

做 K6（413）时先写了个 `body_limit` 分支放在**读 body** 的路径里，结果客户端还是只看到 RST。日志给了答案：

```
HTTP 读取请求头失败：body limit exceeded
```

Beast 的 `request_parser` 在**解析完请求头**时就会拿 `Content-Length` 和 `body_limit()` 比对，超了立刻返回 `body_limit`——也就是说，错误在 `readHead` 的回调里，不在 `readBody`。

所以 413 要在两处都接：

```cpp
// readHead 里：Content-Length 超限走这里
if (ec == boost::beast::http::error::body_limit) { /* 回 413 */ }

// readBody 里：chunked / 流式 body 读到上限走这里
if (ec == boost::beast::http::error::body_limit) { /* 回 413 */ }
```

## 七、回完 413 就 close，会发 RST 把响应冲掉

终于回了 413，客户端却仍然"没收到"——`send_err=ConnectionResetError`。

原理：**接收缓冲区里还有未读数据时调用 `close()`，内核会发 RST 而不是 FIN**。RST 一到，客户端可能连已经到达的响应一起丢弃。而 413 的场景天然就是"对端还在灌数据"。

修法是三步，顺序不能换：

```cpp
// 1) 先半关闭发送方向：FIN 会排在响应字节之后
socket.shutdown(boost::asio::ip::tcp::socket::shutdown_send, ec);

// 2) 把对端残余数据读掉（有上限，防止被无限灌）
drainRemaining = 16 * 1024 * 1024;
drainStep();   // async_read_some → 丢弃 → 递归，直到 EOF / 出错 / 到上限

// 3) 真正关闭
closeSession();
```

实测对比（客户端发 12MB，服务端上限 10MB）：

| | status | recv_err |
| --- | --- | --- |
| 直接 close | `(无响应)` | `ConnectionResetError` |
| shutdown + 排空 + close | `HTTP/1.1 413 Payload Too Large` | `None` |

请求头超限（K7）是同一个套路的 `header_limit` → 431，复用同一段排空逻辑就行。

## 八、空 body 不该被当成控制信号

`httpAsyncReplay(seq, "")` 以前会打印「内容为空，已丢弃」——因为历史上约定"空串 = 暂不回包"。

这个约定会造成非常隐蔽的故障：业务想回 `204 No Content` 或 `200` + 空 body，结果**什么都没发出去**，客户端一直等到超时。而这个"暂不回包"其实**不需要空串来表达**——回调里什么都不做就是不回包。

所以直接删掉那个守卫，让空 body 正常发出 `Content-Length: 0`。凡是"用某个特殊值表示控制语义"的设计，都要问一句：**这个值是不是也会是合法数据？**

## 九、响应头：`set()` 就是覆盖，别自己拼字符串

M1/M3/M4 三个需求（`Set-Cookie` / `X-Request-Id` / `X-Cache`）本质是同一件事：回包接口没有"附加响应头"的入口。加一个名值对列表就够了：

```cpp
using ResponseHeaders = std::vector<std::pair<std::string, std::string>>;

session->httpReplay(body, status, {
    {"Set-Cookie", "sid=abc123; Path=/; HttpOnly"},
    {"X-Request-Id", "req-42"},
    {"X-Cache", "MISS"}});
```

内部就是逐条 `res->set(name, value)`——**同名会覆盖**库自己写的 `Server` / `Content-Type` / CORS 头。这个语义要写进注释，否则业务会以为"我只是追加了一个头"，实际上把默认值改掉了。

## 十、出站 HTTP：Beast 也能当客户端，但 Windows 上必须自己给 CA

M8 是唯一"加新组件"的一项：库里四个库全是 server 侧，没有主动发请求的能力。实现上没什么玄机——Beast 的同步 API 足够：

```cpp
// 明文
beast::tcp_stream stream(ioc);
beast::get_lowest_layer(stream).expires_after(std::chrono::milliseconds(req.timeoutMs));
beast::get_lowest_layer(stream).connect(results, ec);
http::write(stream, message, ec);
http::read(stream, buffer, response, ec);

// https：同一套代码，只是流换成 ssl_stream
beast::ssl_stream<beast::tcp_stream> stream(ioc, ctx);
if (!SSL_set_tlsext_host_name(stream.native_handle(), parts.host.c_str())) { /* SNI 失败 */ }
stream.handshake(ssl::stream_base::client, ec);
```

`beast::get_lowest_layer(stream).expires_after(...)` 的好处是**明文与 TLS 写法完全一致**，超时只设一处。

踩到的两个点：

1. **Windows 上 OpenSSL 的默认证书路径基本是空的**。不指定 CA 就是 `certificate verify failed`。所以 `Request` 里留了 `caFile`：

   ```cpp
   req.caFile = R"(D:\app\Python\Lib\site-packages\certifi\cacert.pem)";  // 现成的 PEM 都行
   ```

   自签证书调试时再退一步关 `verifyPeer`。
2. **`address::to_string(error_code&)` 在 Boost 1.92 被删了**，只剩无参重载。这个在填 `Url::requestIP` 时撞到：`error C2660: 函数不接受 1 个参数`。

另外给自己立了条规矩写进注释：**`Send` 是同步阻塞的，禁止在业务回调（IO 线程）里调用**，否则整条连接的事件循环一起卡死。

## 十一、vcpkg 自身也会坏，而且坏得很误导

这一轮花最多时间的不是代码，是 vcpkg 环境：

| 现象 | 真相 |
| --- | --- |
| `document schema version N is not supported` | 仓库树的 `scripts/vcpkg-tools.json` 与 `vcpkg.exe` 版本不匹配（exe 是 2026-09-26 的，只认 schema 2；切到旧提交反而报 schema 1） |
| `--dry-run` 说"只装 commonnet"，真装却炸 | `--dry-run` 只算计划、**不解析工具数据**，工具链那步根本没走到 |
| `failed to take lock` | 有个 vcpkg 进程（下载卡住被强杀的）一直占着 `installed\vcpkg\vcpkg-running.lock` |
| Boost 1.90 → 1.92 升级中途 `BUILD_FAILED` | 端口树已更新到 1.92，旧包被卸、新包要联网下载，机器上不去 GitHub |

最反直觉的一条：**端口依赖写上去之后，装自己一个包可能触发整棵 Boost 重建**。所以自研端口对 boost 这类大依赖，要么声明清楚并接受升级，要么先不声明、把前置条件写进 `usage`。

## 十二、验证：不要相信"编译过了"

这批 7 项里，有 3 项是**编译能过、行为不对**（空 body、413、431），单靠 `cmake --build` 一个都发现不了。这一轮的验证套路是：

- **原始 socket 探针**：Python 直接拼字节发请求，能看到 RST、能精确控制 `Content-Length` 和头大小。
  - 12MB body → 期望 413 且 `recv_err is None`
  - 20KB header → 期望 431
- **自签证书测 TLS**：`cryptography` 生成 127.0.0.1 的 SAN 证书，Python 起 HTTPS 服务，客户端分别用 `--insecure`（验通路）和 `--cafile`（验校验）跑一遍，最后用**真实公网** `https://example.com` + certifi 的 CA 再验一次。
- **装包之后再用包**：所有验证程序都 `find_package(CommonNet)` 链接**已安装的包**，而不是源码树——否则验证的是"源码能编"，不是"包能用"。

## 经验

- **"我传了参数" ≠ "参数生效"**。`BUILD_SHARED_LIBS` 被 helper 覆盖这件事，只有打开 helper 源码才能看明白。第三方构建系统的行为，永远以源码为准。
- **半新半旧的环境最难查**。exe 新、树旧会报 schema；树新、exe 旧也报 schema；依赖树新、已装包旧会触发整棵重建。判断环境状态要看**版本 + 时间戳 + 哈希**，不要看单一证据。
- **拒绝请求的时机决定错误码走哪条路径**。`Content-Length` 在解析头时就被拒，所以 413 的逻辑要放在 `readHead`，放 `readBody` 永远不触发。
- **`close()` 不是"温和"的**。接收缓冲有未读数据时它会发 RST，把刚写出去的响应一起废掉。要让对方看见拒绝，就得 `shutdown(send)` + 排空 + close。
- **公开头文件的编码是接口的一部分**。UTF-8 无 BOM + LF + 中文注释，缺了 `/utf-8` 就会让下游解析错位；行号偏移是最迷惑的症状。
- **一个功能一个提交**，在排查时值钱：413 和 431 分开提交后，回滚/对比一次只动一处，`git log` 本身就是变更清单。
